# 崩溃诊断：手机进图黑屏崩溃（PE 重定位僵尸条目）

- 日期：2026-09-24
- 现场：`~/Downloads/diagnostics/`（`session-20260924-152201-pid40.log` + 3 个转储 + `EquipSlotDiagnostic.log` 等）
- 症状：同一份客户端，PC 进游戏正常；手机（Wine/Box86 跑 Windows 客户端）进地图黑屏崩溃
- 结论：**不是称号逻辑本身写错，而是 DLL 的 `.reloc` 里残留的 7 条僵尸重定位条目在"被重定位"时改写代码填充区**。
  手机把 DLL 加载到 `0x78700000`（非首选基址）→ 触发；PC 通常落在首选基址 `0x65C80000`（delta=0）→ 条目是空操作，看不出问题。

---

## 一、现场事实（全部来自用户提供的日志与转储）

| 证据 | 内容 |
| --- | --- |
| 崩溃点 | `BeiDouSetItemCompat.dll+0x1ECF`，`code=C0000005`，`ExceptionInformation[0]=1`（写）、`[1]=0x90909090` |
| 寄存器 | `eax=0x78700000`（模块基址）、`ecx=0x787059B0`、`edi=0x78706040`、`esi=0`、`edx=0x7A9E2580`(user32) |

| 第二次崩溃（退出过程中） | `eip=0x09616640`（未知模块，`i0=8` 执行），栈顶返回地址 `WzFileLogger.dll+0x24EF` |
| 运行环境 | 转储模块表含 `winealsa.drv`、`winepulse.drv`、`winex11.drv`、`winevulkan.dll` → **Wine/Box86**，非真实 Windows |
| 模块基址 | `BeiDouSetItemCompat.dll @0x78700000`（首选 `0x65C80000` → delta `0x12A80000`）；`WzFileLogger.dll @0x78610000`（首选 `0x6DD00000`） |

→ **手机上跑的就是这份含 `.titles` 的 DLL**。

## 二、机制推导

`BeiDouSetItemCompat.dll` 的 `.reloc` 共 330 条 HIGHLOW 条目，其中 7 条的目标 DWORD
不是映像内地址，而是代码填充区：

```text
RVA 0x1D87 = 0x90909090     RVA 0x2849 = 0x90909090
RVA 0x1D9A = 0x90909090     RVA 0x28CF = 0x90909090
RVA 0x1E64 = 0x90909000     RVA 0x28D8 = 0x90909090
RVA 0x1EDC = 0x90909090
```

加载器对每条条目做 `DWORD += (实际基址 − ImageBase)`。取手机的实际基址：

```text
RVA 0x1EDC: 90 90 90 90  +0x12A80000  →  90 90 38 A3
```

`RVA 0x1EDF` 恰好是 `.data+0x1F3` 那条 `jmp 0x65C81EDF` 的落点，其后 4 字节仍是 `90 90 90 90`：

```asm
0x78701EDF   A3 90 90 90 90   mov dword ptr [0x90909090], eax
```

→ 一次对 `0x90909090` 的**写入**访问违例，与日志的 `operation=1 / target=90909090` 逐字段吻合。

崩溃现场与该代码块的参数布局也完全一致：`.data+0x1C4` 这个块先用
`call $+5 / pop eax / add eax, 0xFFFFBE1D` 算出 `eax = 模块基址`（日志里 `eax=0x78700000`），
再把 `[esp+4] = base+0x59B0`、`[esp+8]`、`[esp+0xC]`、`[esp+0x10]` 填好，最后 `jmp 0x1EDF`。

> 注：日志/转储记录的 `eip` 是 `0x1ECF`，真实违规指令在 `0x1EDF`（相差 16 字节）。
> 这是 Box86 dynarec 上报指令地址的偏差；违规地址、写入方向、`eax` 与栈布局四项都对得上，
> 足以确证路径。

**第二次崩溃同理**：`WzFileLogger.dll` 有 2 条僵尸条目，正好压在之前修复引入的
位置无关跳转上：

```text
RVA 0x24EC（STUB_A 的 call 0x6640 的 rel32 中段） 与 RVA 0x4413（CAVE_C 的 jmp 0x66B0 的 rel32 中段）
```

重定位后调用/跳转目标被改写 → `call` 到野指针 `0x09616640`，栈顶返回地址
`WzFileLogger.dll+0x24EF` 与之完全对应。

## 三、为什么 PC 不崩、手机崩

- 这些僵尸条目的危害值取决于 delta：`byte[reloc+3] = 0x90 + delta_byte3 + carry`。
  手机固定落在 `0x78700000` → 恰好得到 `0xA3`（`mov [imm32], eax`）→ 必崩。
- PC 上 DLL 若加载在首选基址 `0x65C80000`，delta=0，条目完全不生效 → 一切正常；
  换一个 delta 也可能只是把填充字节改成无害值 → 表现为"偶尔正常"。
- 也就是说：**PC 只是没抽到致命 delta**，隐患一直在（`WzFileLogger.dll` 的同类条目还会破坏
  之前已经修好的两个桩跳转）。

## 四、修复

工具：`tool/client-debug/BeiDouSetItemCompat/fix_dll_reloc_hygiene.py`
（判据：HIGHLOW 条目的目标 DWORD 必须落在 `[ImageBase, ImageBase+SizeOfImage)`；否则删除并打印审计表）

| 文件 | 处理 | 结果指纹 |
| --- | --- | --- |
| `clien/BeiDouSetItemCompat.dll` | 删除 7 条僵尸条目，重建块链 `0x2B0 → 0x2A4` | 20480 B，CheckSum `0x000145E6`，sha256 `4e393447f3ba7c91bb86ba1f529f0207382fc9f76f7684bfc696ca76c4678457` |
| `clien/WzFileLogger.dll` | 删除 2 条僵尸条目 | 43008 B，CheckSum `0x000101C4` |

同时：`patch_nameplate_series.py` 末尾新增第 8 步（自动调用上述工具），
契约测试新增"条目必须指向映像内地址"的断言，并把 `.reloc` 区间加入差异白名单。

**安全性**：文件长度不变；delta=0 时这些条目本来就是空操作，因此按首选基址运行的内存映像
逐字节不变；只有重定位路径从"被破坏"变成"正确"。
