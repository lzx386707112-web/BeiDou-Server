# 套装详情完整显示修复（2026-09-30）

## 现场和根因

用户截图：终极标题显示 `(0/11)`，正文只有腰带、肩章、武器三行，并显示数字 ID。

- 服务端为保证背包悬停匹配，将 11 槽位拆成 8+3，候选超过 10 个也拆成视图。
- DLL 的 RVA `0x2f70` 匹配悬停成员后只渲染当前视图，武器在后一视图，故只有 3 行。
- 运行时发包在 `ItemInformationProvider.getName()` 返回空时输出数字 ID。仓库的
  中英文目录下 Eqp XML 以及随 JAR 打包的装备目录均已有终极中文名称；截图不能
  证明远端部署了同一份 XML，因此不盲改 WZ，而为套装发包增加打包目录回退。
- 上一轮 native 测试在 RVA `0x2f76` 停止，只证明查找，不证明完整绘制。

- `PacketCreator`：候选记录原本忽略的 4 字节字段改为原定义槽位编号（从 1 开始）。
  槽位/候选/视图容量、包长上限、战斗计算、套装定义和激活状态不变。

  正常名称和自定义名称保留，未知装备才继续回退 ID。
- DLL：同 set ID 的全部视图在绘制阶段汇总为候选指针，不扩展原生状态表。
  相同槽位编号合并；优先显示已穿戴候选，其次悬停候选，最后首个候选。
  不同槽位即使同为帽子/戒指也不会合并。旧 JAR 的零字段按装备类型兼容，

  EXE `0x8f32c6..0x8f32ed` 的原生窗口边界是 799/599，此布局沿用该契约。
- 已有字体转换、中文标签、Canvas 绘制、缓存、图层归属、清理入口不变。
  栈增加候选指针区，按 4KiB 探测栈页；未新增客户端钩子、线程或 COM 对象类型。
