# PC 客户端所有角色 MCV 大招不播放 —— 诊断报告

> 日期：2026-09-28
> 诊断对象：`clien/` 客户端（Windows/Parallels，路径 `C:\Mac\Home\Documents\mxd\BeiDou-Server\clien`）
> 证据：`clien/diagnostics/session-20260928-082915-pid6112.log`、`DawnWarriorSkillCompat.log`、`BeiDouVideo.log`、
> `KaringSceneCompat.log`，以及 git 历史中的成功会话 `session-20260828-082236-pid8156.log`。

## 一、结论

**不是某个职业/某个技能的映射问题，而是全局的"D3D8 设备捕获"步骤失败了。**
MCV 播放器 `BeiDouVideo.dll` 从未拿到游戏的真实 `IDirect3DDevice8*`，所以任何通道、
任何角色的 MCV 都画不出来。日志里的直接证据是：

```
clien/BeiDouVideo.log
  player-skill: not initialized
  boss-scene: not initialized
  player-skill: D3D8 device is not attached      ← 触发时设备为空

clien/diagnostics/DawnWarriorSkillCompat.log（本次运行最后三行）
  VIDEO OK: Gr2D_DX8 hook installed
  VIDEO ERROR: no complete D3D8 field-layer hooks were installed within 30 seconds
  D3D8 device is not attached

clien/diagnostics/KaringSceneCompat.log
  ERROR: no attached D3D8 device or compatible BeiDouVideo API
```

`player-skill: D3D8 device is not attached` 说明技能触发链本身是好的（确实调到了
`BDV_PlayFileEx`），只是没有设备可画。Boss 场景通道同样因为"设备未挂载"而全灭。

## 二、失败发生在哪一步（已用反汇编确证）

MCV 播放的对接是**一次性全局捕获**，不是逐技能映射：

```
BeiDou.exe 入口代码洞
  └─ LoadLibraryA("DawnWarriorSkillCompat.dll")      ← 只加载这一个
       └─ BeiDouSkillCompatCore.dll（真正的兼容层，本次 38400 字节）
            ├─ 挂钩 BeiDou.exe 的 LoadLibraryA IAT (0x00AF00C0)
            ├─ Gr2D_DX8.dll 一加载 → 改它的 GetProcAddress IAT 槽
            │     Gr2D_DX8.dll IAT RVA 0x2D024 = KERNEL32!GetProcAddress
            │     （该模块 ImageBase 0x50400000，槽 VA = 0x5042D024）
            ├─ 拦截 GetProcAddress(d3d8, "Direct3DCreate8")
            ├─ 挂钩 IDirect3D8::CreateDevice（vtable 索引 15）
            ├─ 真实设备出现后挂钩设备 vtable 6 个入口
            │     Present=15 SetTexture=61 DrawPrimitive=70
            │     DrawIndexedPrimitive=71 DrawPrimitiveUP=72 DrawIndexedPrimitiveUP=73
            └─ LoadLibraryA("BeiDouVideo.dll") + BDV_AttachDevice(真实设备)
```

Gr2D_DX8.dll 里**唯一**一处解析 `Direct3DCreate8` 的代码就在这条路上，而且它确实是
走 IAT 动态解析（`prefer_dynamic`，非静态导入）：

```
Gr2D  VA 0x50402CF6   push "D3D8.DLL"
      VA 0x50402CFD   call dword ptr [0x5042D010]   ; LoadLibraryA
      VA 0x50402D1A   call dword ptr [0x5042D024]   ; GetProcAddress   ← 被拦截点
      VA 0x50402D2C   call eax                      ; Direct3DCreate8(0xDC)
```

也就是说：**只要没人抢 0x5042D024 这个 4 字节槽，视频就能起来；一旦被抢，整条链在第一步断掉。**

本次运行的日志顺序正好是"抢掉了"：

| 时间 | 事件 |
| --- | --- |
| 08:29:17.093 | `module_load` GR2D_DX8.DLL @0x50400000 |
| 08:29:17.098 | `hook_summary` GR2D_DX8 **total=2 GetProcAddress=1** ← 诊断层把 GetProcAddress 也挂钩了 |
| 08:29:17.104 | `module_load` D3D8.DLL（Gr2D 解析 Direct3DCreate8 就在这一刻） |
| 08:29:17.208 | `hook_summary` GR2D_DX8 **total=1 GetProcAddress=1** ← 同一槽第二次被改写 |
| ~08:29:47 | `VIDEO ERROR: no complete D3D8 field-layer hooks were installed within 30 seconds` |
| 08:31:33.357 | `module_load` BeiDouVideo.dll（**只在第一次放技能时**才被加载） |

兼容层的逻辑与超时位置（`BeiDouSkillCompatCore.dll`，ImageBase 0x67280000）：

- `InstallGr2DHook` @`0x6728334A`：`eax += 0x2D024` 后改写槽；成功打印
  `VIDEO OK: Gr2D_DX8 hook installed`。
- `HookGetProcAddress` @`0x672832E5`：与 `"Direct3DCreate8"`（VA 0x8499）逐字节比较，
  命中则返回 `HookDirect3DCreate8` @`0x67283232`，成功打印
  `VIDEO OK: real Direct3DCreate8 intercepted`。**本次日志里没有这一行。**
- `HookCreateDevice` @`0x67283193`：装完 6 个设备 vtable 钩子后调用 `BDV_AttachDevice`，
  成功打印 `VIDEO OK: D3D8 device attached without a proxy DLL`。**本次也没有。**
- 完整性判定 @`0x672813EB`：要求 6 个全局槽全部非 0；不满足则 300×`Sleep(100)`
  （@`0x67284623` / `0x67284637`）后打印那条 30 秒超时。

> 注意：`VIDEO OK: Gr2D_DX8 hook installed` 只代表"槽被写过一次"，
> **不代表这一枪打中了**。超时那条才是真正的失败标志。

## 三、根因

**视频兼容层与诊断层抢同一个 IAT 槽，视频层输了。**

关键对比（同一台机器、同一个客户端目录，只隔了一次客户端更新）：

| | 成功会话 2026-08-28 | 失败会话 2026-09-28 |
| --- | --- | --- |
| GR2D_DX8 `hook_summary` | **GetProcAddress=0**（诊断层不碰它） | **GetProcAddress=1，且被装了两次** |
| GR2D → D3D8 加载间隔 | 399 ms | 11 ms |
| BeiDouVideo.dll 加载时刻 | 启动后 2.4 s（设备挂载瞬间） | 启动后 **2 分 16 秒**（首次放技能才加载） |
| `DawnWarriorSkillCompat.log` | `Gr2D_DX8 hook installed` / `real Direct3DCreate8 intercepted` / `D3D8 device attached without a proxy DLL` | 只剩 `Gr2D_DX8 hook installed` + 30 秒超时 |

**关键点：视频相关的三个二进制与成功那次逐字节相同**（git blob 一致），所以问题不在视频代码本身：

| 文件 | 成功版(08-28) blob | 现在 blob | 变化 |
| --- | --- | --- | --- |
| 兼容层主体（当时叫 `DawnWarriorSkillCompat.dll`，现为 `BeiDouSkillCompatCore.dll`） | `76d8a905…` | `76d8a905…` | **完全相同** |
| `Gr2D_DX8.dll` | `7502f857…` | `7502f857…` | **完全相同** |
| `BeiDouVideo.dll` | `d663f64f…` | `d663f64f…` | **完全相同** |
| `WzFileLogger.dll` | 25600 字节 | 43008 字节（2026-09-01 换代） | **变了，且新增 GetProcAddress 挂钩** |

回归窗口（08-28 成功 → 09-14 首次失败）里客户端侧的变化：兼容层拆成
"小加载器 `DawnWarriorSkillCompat.dll` + 主体 `BeiDouSkillCompatCore.dll`"、
`WzFileLogger.dll` 从 25 KB 涨到 43 KB（新增 first-chance/会话日志/Flash 守卫等整套诊断）、
`KaringSceneCompat.dll` 更新、新增 `BeiDouWeatherCompat.dll`/`IndexedDamageNumberCompat.dll`、
`config.ini`/`beidou_diagnostics.ini` 改动。

其中**只有 `WzFileLogger.dll` 会写 0x5042D024 这个槽**，而它的 `GetProcAddress=1` 恰好
只出现在失败会话里。注册表式对照（当前会话所有模块）：

```
GR2D_DX8.DLL        total=2 GetProcAddress=1   ← 唯一被挂 GetProcAddress 的渲染模块
CANVAS.DLL          total=3 GetProcAddress=1
其他全部模块         GetProcAddress=0
```

### 为什么输了以后就永久失效

`InstallGr2DHook` @`0x6728334A` 开头就有"已安装"短路：

```asm
6728334A  cmp byte ptr [0x6729158E], 0
67283351  jne 0x6728339B          ; 已安装 → 直接返回，不校验槽内容
```

而 30 秒重试循环每 100 ms 都会调用 `InstallGr2DHook`，却因为这个标志**永远不会发现槽被改写**，
也不会重新抢占。所以表现是"静默失效"：没有报错、没有崩溃，只是视频全都不放。

另外循环里的独立兜底路径（用自己 IAT 里的 `GetProcAddress` 取 `Direct3DCreate8`，
再建一个 1×1 backbuffer 的临时设备来装共享钩子，@`0x672844C2`–`0x67284637`）本次也没成功
——没有打印 `VIDEO OK: shared D3D8 field-layer hooks installed after initialization`。
临时设备创建依赖有效窗口 + 1×1 backbuffer，在任何驱动/时序上都不该作为主路径的兜底。

## 五、正式修复方向（按推荐顺序）

1. **让设备捕获不再依赖 Gr2D 的 GetProcAddress 槽（推荐）**
   兼容层的 30 秒循环本来就是用自己 IAT 里的 `GetProcAddress` 从 `d3d8.dll` 取
   `Direct3DCreate8`（@`0x672844DB`–`0x6728450F`）。把这一步改成：
   取到 `IDirect3D8*` 后**直接改它的 vtable[15]（CreateDevice）**，
   不再创建临时设备、不再碰 Gr2D 的 IAT。
   `d3d8.dll` 的接口 vtable 是进程内共用的，改一次就覆盖游戏后面所有 `CreateDevice`，
   等价于现在"拦截成功"后的效果，但从根上避开槽争用，也不再依赖窗口/1×1 backbuffer。
2. **让重试真正抢占**
   去掉 `0x6729158E` 的短路：每轮都读槽值，若不再是自己的 `HookGetProcAddress`
   就重新写回。改动最小，但仍是"抢槽"模式，诊断层再改一次还会再抢。
3. **让诊断层别挂 Gr2D 的 GetProcAddress**
   `WzFileLogger.dll` 对 `Gr2D_DX8.dll` 的 GetProcAddress 挂钩没有任何诊断价值
   （它只关心 WZ 文件 IO），把该模块排除掉即可。可与 1 或 2 并行。
4. 不建议：放 `d3d8.dll` 代理（文档 §14 已明确禁止作为手机/正式部署项）。

修复 1 或 2 都需要二进制补丁（`BeiDouSkillCompatCore.dll` 无对应源码，
仓库里 `tool/client-debug/dawn-warrior-skill-compat/DawnWarriorSkillCompat.cpp` 是 v43 旧源码，
与现网 v67/v69 成品不一致）。补丁应走 `.codex/skills/beidou-client-binary-patch`，
并同步巡检 `.reloc`，避免重定位僵尸条目。

## 六、复现时不要误判的两点

- `VIDEO OK: Gr2D_DX8 hook installed` **不是成功标志**，只是"槽被写过"。
  唯一成功标志是 `VIDEO OK: real Direct3DCreate8 intercepted` +
  `VIDEO OK: D3D8 device attached without a proxy DLL` + `BeiDouVideo.log` 出现 `device attached`。
- `BeiDouVideo.dll` 的加载时刻本身就是一个指示器：正常应在**启动后几秒内**（设备挂载瞬间）
  出现；如果它直到放技能才加载（本次是 08:31:33），说明设备从未挂载。

## 七、补强证据：Vellum 扩展的失败点（同日追加）

`clien/VellumVideoCompat.log` 给出的是一手现场，比 `hook_summary` 更直接：

```
LOAD: Vellum attack10/11 video compatibility v1
VELLUM VIDEO ERROR: LoadLibraryA chain is not owned by the v69 core
```

对应 `tool/client-debug/vellum-video-compat/VellumVideoCompat.cpp` 的 `InstallHooks`：
它在等核心就绪后断言 `PointerBelongsToModule(*slot, core)`（`slot = BeiDou.exe+0x00AF00C0`），
不成立就 `return 3`——**连自己的 `HookLoadLibraryA` 都不装**。
所以本节把根因表述收窄为：**`BeiDou.exe+0x00AF00C0` 这个 LoadLibraryA 槽在 Vellum 检查时不属于
核心**，核心因此没能在 `Gr2D_DX8.dll` 加载的同一刻装上 `GetProcAddress` 钩子，
只能退到 30 秒轮询（`GetModuleHandleA`）——而 Gr2D 在加载后 **11 ms** 就解析了
`Direct3DCreate8`（见 §三时间线），轮询必然来不及。

已核实的两点前置事实（排除掉两条常见误判）：

- `0x00AF00C0` 确实是**当前** `BeiDou.exe` 的 `LoadLibraryA` IAT（RVA `0x6F00C0`，
  `KERNEL32.dll` 导入表中的第 90 项），核心硬编码的补丁点没错；
- 核心二进制里 `0x00AF00C0` 与 `0x0094F89E` 两个常量都还在，即 v69 仍然会打这两个点。

## 八、已实施的修复（2026-09-28）

**没有改动** `BeiDouSkillCompatCore.dll`、`WzFileLogger.dll`、`BeiDou.exe` 或任何 WZ/IMG。
修复全部落在有源码、可重建、可回归的 `BeiDouVellumVideoCompat.dll` 上，
即 §五的**方向 1**（让捕获不再依赖 IAT 槽）：

1. `InstallHooks` 的两次硬失败降级为 `WARN` 后继续挂链（不再 `return 3`）；
2. 新增 `InstallCreateDeviceVtableHook()`：经 `d3d8.dll` 的 `Direct3DCreate8` 导出自建一个
   `IDirect3D8*`，直接改进程共用的 `vtable[15]`，与任何 IAT 槽无关；
   探针接口**故意不 Release**，避免"每对象虚表"实现下释放刚改过的字节；
3. 渲染判据改为 `AnyChannelHasVideo() && IsOutermostPresentHook(device)`
   （`BDV_Render == BDV_RenderAll`，画全部通道；读设备当前 `vtable[15]` 确认自己是最外层，
   避免与核心重复绘制）。

完整设计、验证与部署步骤见
`tool/client-debug/vellum-video-compat/README.md`；诊断结论与验收指标见该文档第六节。

## 九、v1 实测失败 → 根因修正与 v2（同日）

v1（虚表探针 + 10 ms 轮询）**上机无效**。失败会话
`session-20260928-101750-pid4972.log` 给出了决定性的时间线，本节据此**修正 §七/§八的根因表述**。

### 9.1 时间线：问题是"时间窗"，不是"槽归属"

```
10:17:50.087   Vellum 兼容层加载（比游戏需要设备早约 2.5 s）
10:17:52.578   GR2D_DX8.DLL 加载          (module_load seq=32)
10:17:52.583   诊断器给 GR2D_DX8 装 GetProcAddress 钩子 (hook_summary seq=33)
10:17:52.606   D3D8.DLL 加载              (module_load seq=34, 距 Gr2D 仅 28 ms)
               ↑ 紧随其后 GetProcAddress + Direct3DCreate8 + CreateDevice，全在微秒级
10:19:53.444   BeiDouVideo.dll 才被加载   (seq=475，两分钟后、首次放技能)
```

v1 的兜底是**每 10 ms 轮询 `GetModuleHandleA("d3d8.dll")`**，平均晚 5 ms、最坏 10 ms
才能打上虚表补丁 —— 而客户端早已把设备建完。

### 9.2 日志自证

v1 的 `clien/VellumVideoCompat.log` 只有 4 行，**最后一行是"捕获成功"，之后再无任何一行**：

```
LOAD: Vellum attack10/11 video compatibility v1
VELLUM VIDEO WARN: LoadLibraryA slot is not owned by the v69 core; chaining defensively
VELLUM VIDEO OK: runtime hook chain ready
VELLUM VIDEO OK: IDirect3D8::CreateDevice captured without an IAT race   ← 补丁打上了，但太晚
```

`HookCreateDevice`（会打 `D3D8 device attached` / `could not attach`）与
`HookLoadLibraryA`（Gr2D、D3D8 加载时各该打一行）**一行都没出现**。二者互证：
虚表补丁落在 `CreateDevice` 之后。

### 9.3 顺带确认：诊断器确实在抢 IAT 槽

同一会话的内存转储（`high-cpu-20260928-101750-pid4972-36820015.dmp`）中：

- `BeiDou.exe` 里 `LoadLibraryA` 槽 `0x00AF00C0`、`Gr2D_DX8` 里 `GetProcAddress` 槽
  `0x5042D024` **都不在转储页内**（诊断器 dump 只带部分页）；
- 但 **Vellum 模块内有指针落在 `WzFileLogger.dll` 地址区间**（`6C5D3038 -> 6C2554xx`，
  核心模块内也有同类指针）→ 我方的"原函数"被保存成了诊断器的钩子，说明诊断器
  在模块加载时会**重写 `BeiDou.exe+0x00AF00C0`**，把别的 `LoadLibraryA` 钩子挤出链外。

**修正后的根因**：不是"两个模块抢槽"本身，而是**任何依赖 IAT 槽或轮询的捕获都太晚**。
槽争用只是让"同步通知"这条路也失效了。

### 9.4 v2 修复（已实施，待真机验收）

不再碰任何 IAT 槽、不再轮询：

1. `InstallHooks` 里**自己预加载 `d3d8.dll`**（实测早于 GR2D 约 2.5 s）；
2. 直接给 **`d3d8!Direct3DCreate8` 的函数体打 5 字节 `jmp` + trampoline**
   （导出转发先跟随；前 5 字节不可搬迁就降级到探针方案，绝不盲打；
   写入**先操作数后操作码**且走 `volatile`）；
3. `HookDirect3DCreate8` 拦到客户端**自己的** `IDirect3D8*`，直接改它的 `vtable[15]`
   —— 与"虚表是否进程共用"无关；另建探针做对照并在日志里写明是 shared 还是 per-object；
4. 20 秒看门狗：成功 `capture confirmed by a live D3D8 device`，失败
   `no D3D8 device was observed within the capture window`（下次一眼可判）。

文件 8704 → **9216** 字节，sha256 `d0e42d9aded5d1c991fdfe06ddebdc9a83132f62e9984471a1683332d4f82f83`；
`test_contract.py` **11 项全过**（含"代码里不得再出现任何 IAT 槽"与
"出厂文件大小不得等于上一版"两条新硬约束）。**真机运行验收尚未完成。**

```
boss-scene:    device attached
player-skill: playback queued
```

**设备捕获这一环彻底解决了**（v2 方案正确）：设备已挂在播放器上，核心也确实调了
`BDV_PlayFileEx(PLAYER_SKILL, …)` 并成功入队。但用户侧画面仍无变化。

### 10.2 新根因：`IsOutermostPresentHook` 恒为假

v2 的 `HookPresent` 里有一道门 `IsOutermostPresentHook(device)`，它比较设备
`vtable[15]` 与本模块 `HookPresent` 的地址。该判定**恒为假**，因为
`KaringSceneCompat.dll` 把它的 Present 钩子链在**我们之上**：

* `clien/KaringSceneCompat.log` = `OK: chained after Dawn D3D8 hooks`
  （它的安装发生在我们的钩子之后）；
* 反汇编（基址 `0x6D840000`）：`0x6D84148C lea eax,[ebx+0x3c]` 读设备 vtable[15] →
  `0x6D8414A7 mov [0x6D84313C],eax` 保存"上一层"（即本模块 `HookPresent`）→
  `0x6D84148F call 0x6D8412E7` 写回自己的 `0x6D8416C8`；随后每帧在
  `0x6D84176E call dword ptr [0x6D84313C]` **无条件回调我们**。
  它同样链式接管了 `[ebx+0xf4]/[ebx+0x118]/[ebx+0x11c]/[ebx+0x120]/[ebx+0x124]`
  （SetTexture + 四个 Draw*）——正是我们装的那 6 个槽，与转储中"Karing 数据段里 6 个
  指向 Vellum 的指针"完全对应。

所以我们的 `HookPresent` **每帧都在跑**，但 `vtable[15]` 此刻是 Karing 的
`0x6D8416C8`，判定"我不是最外层"→ 一帧都不画。

另外两个可能渲染的层也都不画：

* Karing 只在**它自己的 boss-scene 视频**播放时才调 `BDV_RenderAll`
  （`0x6D8416C8` 开头 `cmp byte ptr [0x6D8430A0],0`，为 0 直接跳到 `0x6D84174C` 透传）；
* v69 核心的 field-layer 钩子从未装上
  （`VIDEO ERROR: no complete D3D8 field-layer hooks were installed within 30 seconds`）。

⇒ 除本模块外**没有任何一层会画 player-skill 通道**，渲染绝不能以"我在最外层"为前提。

### 10.3 v3 修复

1. **删除 `IsOutermostPresentHook` 与那道门**：渲染条件只剩"任一通道处于
   `DECODING/PLAYING`" + "本帧未画" + `gRender != nullptr`；
2. **新增每 2 s 的通道健康日志** `VELLUM VIDEO STATUS: channel=… state=… decoded=…
   displayed=… dropped=… position=…ms`（`state=4` 时附 `error="…"`）；

   （v2 每次都会新建一个不释放的探针接口）。

`a14900bec1b035008c546e222a3ee34d666e5346a02e55b4c80756ba755cef7a`；

## 十一、v3 之后能播了，但飘字被视频盖住 —— 插入点在 Present 而不是 FIELD_EFFECT（同日续）

### 11.1 症状与判定

用户反馈：**"能播放了，但是修改之后飘字就不显示了，又或者说被动画遮挡了。"**
这**不是**崩溃、不是解码失败、不是设备问题：视频确实在画，只是画在了整帧最上层。

判定依据是 14:10 那轮会话（`clien/VellumVideoCompat.log`，40941 字节，v6）：

```text
OK: d3d8 Direct3DCreate8 code hook installed ahead of the client (relocated 5 whole prologue bytes)
OK: capture confirmed by a live D3D8 device
OK: D3D8 device attached
OK: video frames are presented through the chained Present hook     ← 走的是 Present 兜底
VELLUM VIDEO STATUS: channel=0 state=2 decoded=29  displayed=26  position=1635ms
VELLUM VIDEO STATUS: channel=0 state=3 decoded=117 displayed=115 position=7631ms   ← 播完
（其后 224 条 STATUS 全部是 channel=0 的 FINISHED 轮询，position 一直涨到 141465ms）
```

* 通道是 `channel=0` = **player-skill**，即核心按技能 ID 起播的（`BeiDouVideo.log` 两条
  `player-skill: playback queued`、`VIDEO OK: Spirit Caliber started` ×2）；
* 全程**没有** `attack10/11 screen started`、没有 `boss-scene: playback queued` ——
  本模块自己的标记路径一次都没命中；
* 因此 Present 兜底是唯一渲染路径 ⇒ 视频被画在 `EndScene` 之后、`Present` 之前。

### 11.2 为什么这不是"解码/钩子"问题，而是"层级"问题

这个项目**早就**为 MCV 定下了插入点，写在两处文档里：

* `tool/client-video/README.md`「最终层级方案」：
  > 旧大帧版本的伤害飘字正常，说明原 `Map/Effect.img` 的 FIELD_EFFECT 绘制时机已经满足
  > 技能演出的层级要求。最终方案因此保留这个已验证的插入点……
* `docs/tools/beidou-video-dll-integration.md` 排查表：
  > 技能层压住 UI/飘字 → draw 插入点 → **优先使用已验证 FIELD_EFFECT marker 层，不要随意
  > 移到 Present**

机制：服务端只给施法者发一次 `PacketCreator.showEffect("customSkill/<职业>/<技能>VideoLayer")`，
对应 `Map/Effect.img` 节点只有**一张 7x5 Canvas、delay 30000 ms**，所以客户端在整个视频期间
**每帧都从技能特效层画这一张小图**（在飘字与 UI 之前）。兼容层在这一次 draw 上改调
`BDV_Render()` 并吞掉标记本身，就得到正确的原生顺序。

**本模块到 v6 为止只实现了 Root Abyss 那一族签名**（`F357/F689/FABC/FDEF` + 第 5 像素 code
5/6），没有实现 FIELD_EFFECT 那一族（`F123/F456/F789/FABC`；A8R8G8B8 为
`FF112233/FF445566/FF778899/FFAABBCC`）。于是每个技能 `DetectMarker` 都返回 0 →
`gMarkerBound` 永假 → 标记 draw 原样交给客户端 → 只剩 Present 兜底。

> 同一份签名判定在核心 `DawnWarriorSkillCompat.cpp` 的
> `DetectVideoMarkerPixels`/`DetectVideoMarkerTexture` 里是有的（code 0 = FIELD_EFFECT 位置
> 标记），但核心的 D3D8 field-layer 钩子从未装上（它依赖 Gr2D 的 `GetProcAddress` IAT 槽）；
> 本模块的 d3d8 导出代码钩子才是可用的那一条，所以判定必须补在这里。

### 11.3 v7 修复（`clien/BeiDouVellumVideoCompat.dll`，20480 字节）

1. 新增 `MarkerSignature.h`（无 Windows 依赖，可被宿主 harness 编译）承载两族签名；
2. `DetectMarker` 返回 `Hit{kind, code}`：`kFieldEffect`（只标记位置）与
   `kVellumScene`（位置 + code 5/6 选片）；三个格式 A4R4G4B4/A8R8G8B8/X8R8G8B8 全覆盖；
3. **渲染点从 Present 移到标记 draw**（`ConsumeMarkerDraw`），条件
   `gVideoPlaying || AnyChannelHasVideo()` —— 核心起的 player-skill 播放也会画在标记位置；
4. **只吞标记自己那一次 draw**：v6 之前 `gMarkerBound` 要到帧末才清，标记之后、下一次
   stage-0 `SetTexture` 之前的所有 draw 都被静默丢弃（本帧飘字若落在窗口里会整段消失）；
5. **Present 明确降级为兜底**：日志改为 `VELLUM VIDEO WARN: Present fallback active
   (no field-effect marker was drawn)`，并新增每次播放一条
   `VELLUM VIDEO SUMMARY: marker_frames=N present_fallback_frames=M`
   —— `M>0` 即"这个技能的视频在盖飘字"，且原因在资源/服务端侧；
6. 新增 `FIELD_EFFECT marker texture recognised`（每会话一次）与两行 `LAYER:` 契约日志。
