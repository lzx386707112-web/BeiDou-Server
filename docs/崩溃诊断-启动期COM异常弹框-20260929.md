# 崩溃诊断 — 启动期 COM 异常弹框退出（会话 20260929-003654-pid24680）

> 用户反馈「崩溃，报错参数错误」。
> 素材：`~/Downloads/diagnostics/`（8 个兼容层日志 + `session-20260929-003654-pid24680.log` + `first-chance-cpp-*.dmp` + `exit-process-*.dmp`）。
> 客户端：`F:\SF\暖暖083\`（SizeOfImage `0x00A94000`、`WzFileLogger.dll` 43008 / `DawnWarriorSkillCompat.dll` 9728 / `BeiDouSetItemCompat.dll` 20480，与仓库 `clien/` 逐一对齐 ⇒ 就是仓库这一套部署）。

## 一、结论速览

1. **这不是崩溃。** 全日志无 `event=crash`、无 `first_chance_av`、无访问违例（`C0000005`）、无 `window_lost`。
   结局是 `event=process_exit api=ExitProcess code=0`（**干净退出**，`tid=2540` 主动调用）。
2. **是 3 次未处理的 C++ 异常**（`0xE06D7363`）被客户端自己的异常过滤器接管 → **弹框** → 约 2 秒后主动退出。
   过滤器转交记录 4 次：`event=exception_filter action=preserved_client_filter`。
3. 三次异常的**类型已确证为 `class _com_error`**（解析 ThrowInfo 的 TypeDescriptor 名得到 `.?AV_com_error@@`），即 **COM 调用失败**，不是渲染或内存问题。
4. **已读出两次异常的真实 HRESULT：`0x80004003`（`E_POINTER`，"无效指针"）**，见 §二.4。
5. occ2 的**抛点精确落在 `BeiDou.exe!0x402648`** —— 就是引擎里那个"取到空指针则抛 `0x80004003`"的访问器（函数入口 `0x40263B`）。
6. ⚠️ **`0x80004003` 在中文系统显示的是「无效指针」，不是「参数错误」。**「参数错误」对应 `0x80070057 E_INVALIDARG`。
   整套 `BeiDou.exe` 里 `push 0x80070057` **只有 3 处**（`0x402FC6` / `0x45B7EE` / `0x85904D`），全部在 COM/VARIANT 包装层。
   ⇒ 用户看到的弹框文字与本次抓到的 hr **对不上**，必须先拿到弹框原文（见 §四）。

### 3. 异常类型 = `_com_error`（已解析）

两个 `pTI` 按 `{attributes, pmfnUnwind, pForwardCompat, pCatchableTypeArray}` 展开，链路完全自洽：

```
NameSpace.dll!0x50819008  → CTA 0x50819000 {n=1, arr[0]=0x50818FE0}
                          → CatchableType.pType = 0x5081D1D0
                          → TypeDescriptor.name = ".?AV_com_error@@"

BeiDou.exe!0x00B44B18     → CTA 0x00B44B10 {n=1, arr[0]=0x00B44AF0}
                          → CatchableType.pType = 0x00BD8270
                          → TypeDescriptor.name = ".?AV_com_error@@"
```

⇒ **occ1 是 `NameSpace.dll` 里编译的 `_com_error`；occ2/occ3 是 `BeiDou.exe` 里编译的 `_com_error`。**

抛出实现（`BeiDou.exe`）：

```
0xA5FDE4: push 0 ; push [esp+8] ; call 0xA605C3 ; ret 4     ← 所有内联抛点的公用 thunk
0xA605C3: push ebp ; mov ebp,esp ; sub 0x10,esp

          push [ebp+0xC] ; push [ebp+8]             ; _com_error(hr, perrinfo) 在栈上构造
```

（旁证：occ3 的栈 `0x19EBE8` 处正好压着 `0x00A605E7`，即这条 throw 序列的返回痕迹。）

### 4. HRESULT 读数

`first-chance-cpp-*.dmp` 携带的异常流是 **occ1** 的（`pObj=0x0019C04C`），而该地址**落在转储未覆盖的低栈区**
（转储里 `tid=0x9EC` 的栈范围是 `0x19DEE8..0x1A0000`）⇒ `dump_inspect.py exc` 报「不在转储内存里」，occ1 的 hr 读不到。

但 **occ2/occ3 的异常对象还在栈上**，直接读出来：

```
0x0019EBF4 (occ3 == params[1]) :
   +0x00 0x00B41240   [BeiDou.exe+0x741240]      ← vfptr / 静态表
   +0x04 0x80004003   E_POINTER  「无效指针」     ← m_hr  ★
   +0x08 0x00000000

0x0019EC08 附近的第二份副本:
   +0x00 0x009F6108
   +0x04 0x80004003   E_POINTER                  ← 又一份
```

⇒ **occ2、occ3 的 hr 都是 `0x80004003`**。（`+0x4 = _com_error::m_hr` 的读法与既往结论一致。）

### 5. 抛点定位

`occ2` 栈上 `0x40264D` 是精确返回址，而 `0x402648` 的指令正是 `call 0xA5FDE4`：

```
0x40263B: push %esi ; mov %ecx,%esi
0x40263E: cmpl $0x0,(%esi)
0x402641: jne  0x40264D
0x402643: push $0x80004003     ← 硬编码 E_POINTER
0x402648: call 0xA5FDE4        ★ occ2 的抛出点
0x40264D: mov (%esi),%eax ; pop %esi ; ret
```

这是引擎的「**空则抛**」访问器（`this->ptr == 0` 就抛 `E_POINTER`）。
整个 `BeiDou.exe` 里 `push 0x80004003` 有 **4927 处**（几乎全是这一族的展开），所以"抛 E_POINTER"本身是引擎的常规表达方式，**关键在上游为什么拿到空值**。

`occ1` 的 `NameSpace.dll` 侧：`0x50805293` 是 `call 0x5080E0D8` 的返回址，而 `0x5080E0D8` 是 **IAT thunk**
（`jmp *[0x50817058]`，实为 `memcpy`/`wcscpy` 一类的 CRT 导入），所以 occ1 的抛点在 NameSpace.dll 内部更深处，
**栈候选没有覆盖到**，需要靠 `VellumVideoCompat.log` 的 `*` 标记（见 §四）。

### 6. 「参数错误」的可能来源（尚未定案）

| 文案 | HRESULT | 在 `BeiDou.exe` 中的抛点 |
|---|---|---|
| 无效指针 | `0x80004003` E_POINTER | 4927 处（含已确证的 `0x402648`） |
| **参数错误 / 一个或多个参数无效** | `0x80070057` E_INVALIDARG | **仅 3 处** |

三处 `push 0x80070057` 全部紧跟同一个 throw thunk，均为 COM 包装层：

```
0x402FC6  函数 0x402FAB：cmpw 参数 vs {3(VT_I4), 0xA(VT_ERROR), 0xB(VT_BOOL)}，其余抛 E_INVALIDARG
0x45B7EE  函数 0x45B7DA：cmpw 参数 vs {5(VT_R8), 7(VT_DATE)}，其余抛 E_INVALIDARG
0x85904D  内联于某函数（无 `call 0x85904D` 站点），紧邻 `mov 0x8(%ecx),%al / sub 0x8(%edx),%al`
```

另外确认：
- `BeiDou.exe` / `NameSpace.dll` / `WzFileLogger.dll` **内部没有任何中文错误文案**
  （`参数错误`/`指针无效`/`无效参数` GBK 与 UTF-16 计数全为 0）⇒ 弹框文字必然来自**系统消息表**（`FormatMessage`），
  即 `_com_error::ErrorMessage()` 的输出。
- 因此**若弹框真是「参数错误」，那 hr 就该是 `0x80070057`**，与 §二.4 读到的 `0x80004003`（「无效指针」）不一致。

**两种解释，二选一（需要弹框原文才能定）：**
- **(A) 弹框显示的是 occ1**（`NameSpace.dll` 抛的 `_com_error`，hr 未能读出）—— 它的 hr 可能正是 `0x80070057`。
- **(B) 用户是口语化转述**（把"无效指针"说成"参数错误"），或者是另一处未被本次日志记录的对话框。

## 三、与既往「切图无效指针」的关系

同族（都是 COM 层拿不到东西 → `_com_error`），但**不是同一次问题**：

- 既往那轮（`docs/崩溃诊断-切图无效指针-20260928.md`）是**切图时 14 次** `_com_error`；
  本次是**启动后 16 秒、只有 3 次**，且 `health` 全程 responsive。
- 当前 `clien/BeiDou.exe` 确认仍是 **P5 版**，规格逐项复核通过：

| 检查项 | 期望(P5) | 实测 |
|---|---|---|
| `call 0x40263B` 总数 | 2406−127 = **2279** | **2279** ✓ |
| `0x5CAC3D..0x5CF58C` 内 `call 0x40263B` | 0 | **0** ✓ |
| 同区间 `call 0x403935`（桩D壳） | 119 | **119** ✓ |
| 同区间 `call 0x409EEF`（桩G壳） | 2 | **2** ✓ |
| 桩E `0xAEFEA0` | `8B 01 C3`（`mov eax,[ecx]; ret`） | ✓ |

⇒ **本次三次异常都不在 P5 修的切图函数里**（`0x402648` 属 P5 区域外的 2279 处站点之一），
P5 的"三壳"没有参与，所以不能按"切图那套"继续打补丁。

## 四、待补材料与下一步

### 优先级 1：取 `VellumVideoCompat.log`（`BeiDouVellumVideoCompat.dll` v6 观察者的日志）

**本次会话的三次异常现场，它每次都写了日志** —— 证据是 `session` 日志里每次 `first_chance_cpp` 之后，
同一故障线程（`tid=2540`）立刻 `resource_open ... path="VellumVideoCompat.log"`：

```
10.628  resource_open  path="VellumVideoCompat.log"   ← occ1 之后
10.629  resource_open  path="VellumVideoCompat.log"   ← occ2 之后
10.630  resource_open  path="VellumVideoCompat.log"   ← occ3 之后
10.887  resource_open  path="VellumVideoCompat.log"
```

该文件里应有 `FIRST-CHANCE CPP: … hr=0x… stack="sNN:+0x…*"`，其中 **`hr=` 是逐次真实 HRESULT，带 `*` 的那一项就是抛点**
—— 这能一次性给出 **occ1 的 hr（决定弹框到底是"无效指针"还是"参数错误"）** 和三个抛点地址。
⚠️ 它**不在** `diagnostics\` 目录里（`diagnostics` 只收 `session-*.log` 与各 `.dmp`），要在客户端根目录（`F:\SF\暖暖083\`）找。

### 优先级 2：弹框原文/截图 + 复现条件

- 弹框的确切文字（是「无效指针」还是「参数错误」？标题栏是什么？）
- 出错前在做什么：是**登录中/登录后立即**，还是**进某张图/切换 UI**？
- 是否必现；换个账号/角色是否一样。

### 优先级 3：把过滤器的 hr 打进会话日志（**本次分析最大的信息缺口**）

现在 `event=exception_filter action=preserved_client_filter` **不带任何异常信息**，
每次都要靠 dmp 反推、且低栈区一旦没进转储就读不到。
建议在 `WzFileLogger` 的 filter 记录里补 `ExceptionCode` + `ExceptionInformation[0..3]`
（对 `0xE06D7363` 就是 magic / pObj / pTI，而 `pObj+4` 就是 `m_hr`）。
这样以后 `session-*.log` 单文件即可定案。

若短期不改 DLL，可用的等效手段：把 `dump_first_chance_cpp_after` 设成**每次异常都落转储**
（本次 3 次 ≈ 30 MB，可接受），避免只留第一份、而第一份恰好是低栈区读不到的那次。

## 五、附：环境侧值得留意的三件事

1. **`KaringSceneCompat.dll` 是在异常之后才被加载的**（`00:37:10.634`，`tid=11504`，与写转储同刻）。
   它不在启动期的 `hook_summary` 序列里，属延迟加载。虽然与本次 `_com_error` 无直接因果，
   但"异常后才加载的兼容层"应当记一笔，后续若复现需观察它的加载时机。
2. 宿主环境注入较多：**深信服 SSL VPN**（`SangforUDProtectEx/…dll`）、**搜狗输入法**（`SogouPY.ime` + 7 个组件）、
   `Karing` 相关 D3D8 链。这些都会出现在 `incident_module` 清单里，排查时不要误认成游戏模块。
3. 转储时刻主线程 EBP 链落在 **渲染路径**（`amdxn32 → d3d8 → Gr2D_DX8 → BeiDou.exe+0x2398A1 → …`），
   进一步确认**不是死循环/卡死**，与既往 `sustained_high_cpu` 的判读一致。
