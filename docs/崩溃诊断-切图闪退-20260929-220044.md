## 〇、一句话结论

**不是硬 AV 崩，是"进图后某 sprite 画布帧在图形层解码/建纹理时取空 → `_com_error(E_POINTER)` 抛出 → 客户端顶层异常过滤器决定收尾 → `ExitProcess(0)`"**。
症状就是玩家看到的"切图闪退"。抛出点落在 `BeiDou.exe` 的 `0x40A492` / `0x40A50E`
（两处 `call 0x40263B`），**这两处不在 P5 的覆盖范围内**。
⚠️ **2026-09-30 修正早期判断**：本 dump 的异常线程栈落在 `Gr2D_DX8.dll`（图形层），
说明至少一次抛出发生在**建纹理/画布解码**阶段，而非 WZ 属性访问；
这与"自由市场里同样抛了 8 次都被容忍、唯独 occ9/10 逃逸"完全吻合——
逃逸的那次大概率卡在某个 sprite 的坏帧上。成因仍是同源的 `_com_error`，只是
**故障域从「WZ 节点缺失」收窄到「9001105.img 的某个画布帧图形层解码失败」**。

## 三、异常本体

- `code=0xE06D7363`（MSVC C++ throw），`pThrowInfo=0x00B44B18`
  → `_CatchableType → _TypeDescriptor 0xBD8270 = ".?AV_com_error@@"`（与 09-29 手机那次同一类）。
- hr：本次会话的 `VellumVideoCompat.log` 没被拷出来；**同一抛链**的 hr 由本机观察者日志
  `clien/VellumVideoCompat.log`（今天 08:31 会话）直接给出 —— 58 条全是 `hr=0x80004003 E_POINTER`。
  （⚠️ 转储里 `pObject+0x4` 读出来是栈残留 `0xC3D48000`，不可信；按 MEMORY 的规矩只认观察者日志/弹框。）
- 抛链（objdump 逐条核对，**返回址与日志完全对上**）：

```
NAMESPACE.DLL+0x15478  /  PCOM.DLL+0x391D        ← WZ 资源访问层
  → 0x40A50E: call 0x40263B   返回址 0x40A513     （occ 2/3/4/5）
  → 0x40A492: call 0x40263B   返回址 0x40A497     （occ 6/7/8）
     0x40263B  "[ecx]==0 就抛 0x80004003"
       → 0xA5FDE4 _com_raise_error → 0xA605C3 → 0xA60BEB _CxxThrowException
  下游紧接 0x40A499 / 0x40A515: call 0x403935（vtbl[5] VARIANT 出参包装）
```

- occ 1（22:00:51.412）栈里是 `d3d11 / nvgpucomp32 / CANVAS.DLL`，是 D3D 初始化期的抛出，**与本次无关**。
- **本 dump（2504203）的异常线程栈在 `Gr2D_DX8.dll` 图形层**（EBP 链：`BeiDou.exe+0x2398A1 / +0x12950C / +0x5F69DD / +0x5F5219 / +0x665417` ← `Gr2D_DX8.dll+0x888C/E558/2B26/9385/3D07`）。
  这证明**至少一次 `_com_error` 是在图形层（建纹理/画布解码）抛出的**，不是 WZ 属性访问层——
  推翻了早期"纯 WZ 取空属性"的单一定性。本质是同一个抛点（`[ecx]==0 → _com_error`）被
  不同上层调用：WZ 访问层**和**图形解码层都会走到它。
- 结合"自由市场里同样抛了 8 次都被容忍、唯独 occ9/10 逃逸到顶层过滤器"，最一致的机理是：
  **occ2~8 = 同图其他玩家的坐骑/勋章在图形层建纹理时的可容忍 `_com_error`；occ9/10 = `Npc\9001105.img`
  的某个画布帧在图形层解码失败，且这一帧没被 `catch(_com_error&)` 接住 → 逃逸 → 收尾退出。**
- occ 9/10 是 `cpp_stack_samples=8` 之后的 `(sample_limit)`，**没有栈**，但它们紧跟
  `String\Npc.img` + `Npc\9001105.img` 的加载（相隔 1~3 ms）—— 这是目前最强的"最后一根稻草"线索。

## 五、为什么 P5 没挡住

- P5 只把 `0x5CAC3D..0x5CF58C` 区间内的 **127 个 `call 0x40263B`** 改指桩E（`0xAEFEA0 = mov eax,[ecx]; ret`），
  再配桩D/F/G 接下游。
- `0x409EEF` 那个"桩G"是**函数入口**的守卫（`test esi,esi; je → xor eax,eax; ret`），只挡 `this==0`，
  **挡不到函数体内部的 `call 0x40263B`**。
- ⚠️ **修正一条旧笔记**：`MEMORY-客户端崩溃.md` 里写"`0x40A492` 所属函数入口 `0x409EEF`"——
  objdump 显示 `0x409EEF` 的函数体在 `0x409F15` 就 `ret` 了，装不下 `0x40A492`；
  区间内除 `0x409EEF` 外**再无 `55 8B EC` 序言**，真正的大函数入口是
  **`0x409F9F`**（`mov eax,0xA76076; call 0xA60B98` 的 EH 序言）。
  **动补丁前必须再核一次函数边界**（用 objdump，别用 capstone 线性回扫）。
