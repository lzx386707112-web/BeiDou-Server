一、结论速览

一句话：数据面（地图/任务/life/怪物/道具）基本齐；缺的是「玩法逻辑」与「导航入口」两块。

  • 齐的：60 张地图的几何与 life 布点（怪物数量与 TMS 逐一相同）、16 条主线任务的四件套定义（客户端 IMG 与服务端 XML 完全一致）、7 只相关怪 + 3 个任务道具的资源、8 个 portal 脚本、3 个 event 脚本。
  • 缺的（三块）： ① 61 张 TMS 地图（272020500 + 272020600–272020659 的「囚禁空间」分房）； ② 46 张图的 info 钩子（fieldScript / onUserEnter / onFirstUserEnter / fieldType / mode）； ③ 8 条任务没有脚本文件、且 Check 里的 startscript/endscript 一并被剥离（设计上「无过场」，但这两个动作是绑定的，将来补脚本必须同时补钩子）。
  • 机制差异是根因，不是遗漏：BeiDou 服务端完全不读 fieldScript（grep fieldScript src/main/java 零命中）。TMS 那套「场地脚本 = 副本逻辑本体」（akayrum / akayrum1 / akayrum_cygnus / AkayrumShadow / GerectorShadow）在 BeiDou 没有对应实现，因此本区被改写成 portal 脚本 + event 脚本驱动 —— 这部分是齐的。

三条硬结论

  • 钩子与脚本文件是严格配对的：凡是 BeiDou 有 quest/<id>.js 的 8 条（31165/31170–31174/31176/31179），startscript 就保留；没有脚本文件的 8 条，钩子一律剥掉。这是有意为之的「无过场、纯数据驱动」设计，不是随机丢失。
  • 但两者是耦合的：BeiDou 的任务脚本按任务 ID取（QuestScriptManager:53 → "quest/" + questid + ".js"），而是否调用由 Check 里的 startscript/endscript 决定（Quest.hasScriptRequirement()）。所以将来补了脚本文件，还必须把 startscript/endscript 补回（客户端 IMG + wz + wz-zh-CN 三处），否则脚本永远不会被调用。q31166s 这类 TMS 脚本名在 BeiDou 里无意义，不必照抄。
  • 奖励被统一压平：TMS 逐条不同（301891 ~ 18 548 393），BeiDou 一律 301891（31165/31170–31174/31179 无 EXP）。是平衡策略还是漏改，需要你确认。

  • 2026-09-29 已修正：过去的神木村（272000100 燃燒的神木村1）原先没有直通入口 —— 中心城 272000000 的 timeCrack 门按任务状态分流（31180 完成→272030000；31167 进行中→272000100；否则→272020000），没做该任务线的玩家进不去。现已在万能传送的「未来之门」列表新增「过去的神木村」一条。
