## 一、版本核对：对方跑的确实是旧构建

`WzFileLogger` 自检把每个文件的写入时间打进了日志（FILETIME，UTC）；加 8 小时与本机
构建时间对照，逐一对上：

| 文件 | 对方文件写入时间(+08:00) | 本机构建时间 | 判定 |
|---|---|---|---|
| `WzFileLogger.dll` | 2026-09-23 20:40:55 | flash 槽位补丁产出时刻 20:40:55 | **修复前**（reloc 修复在 09-24 15:35） |
| `BeiDouSetItemCompat.dll` | 2026-09-24 13:52:10 | 称号系列补丁产出时刻 13:52:10 | **修复前**（reloc 修复在 15:35 同一分钟重写） |
| `DawnWarriorSkillCompat.dll` | 2026-09-23 20:04:48 | 20:04 | 同一版 |
| `WzFlashRenderer.dll` | 2026-08-21 07:22:29 | 原版 | 同一版 |

`BeiDou.exe` 无法从日志取哈希，但用 PE CheckSum 反查：本机
`clien/BeiDou.exe` = `0x00820778` / sha256 `b8e6cc8b…4f726`，
与 14:24 那份转储里记录的 CheckSum `0x00820778` 完全一致 → **exe 是同一版，不需要换**。

结论：**只有 2 个文件需要重新发货**。

## 二、根因：`call STUB_A` / `jmp CAVE_C` 的 rel32 被加载器改写

`WzFileLogger.dll` 的 flash 槽位补丁在 `.text` 尾部放了三段桩，并把两处调用改成
位置无关的 rel32 跳转：

```asm
0x24EA: E8 51 41 00 00   call 0x6640   ; STUB_A
0x4411: E9 9A 22 00 00   jmp  0x66B0   ; CAVE_C
```

但 `.reloc` 里仍有两条旧布局时代的 HIGHLOW 条目，目标 DWORD 落在 rel32 中段：

```text
RVA 0x24EC -> 原值 0x90000041     （压在 call STUB_A 的 rel32 上）
RVA 0x4413 -> 原值 0x90000022     （压在 jmp  CAVE_C 的 rel32 上）
```

加载器执行 `dword += (实际基址 − 0x6DD00000)`，于是 rel32 被改写。
把两条规则写成算式后，可以**从日志里的 eip 直接反解模块基址**：

```text
site A: rel32 = 0x51 | (((base - IB + 0x41) & 0xFFFFFF) << 8) ; target = base + 0x24EF + rel32
site C: rel32 = 0x9A | (((base - IB + 0x22) & 0xFFFFFF) << 8) ; target = base + 0x4416 + rel32
IB = 0x6DD00000
```

### 三条互相独立的对账（全部命中）

| 证据来源 | 已知量 | 反解出的 `WzFileLogger` 基址 | 正算另一处 |
|---|---|---|---|
| 手机崩溃转储（Wine/Box86） | `call` 目标 `0x09616640` | `0x78610000`（转储模块表实测） | — |
| 对方 PC 本次会话 | `EQUIP EXCEPTION eip=0x198A6640` | `0x5F8A0000` | site C → `0x198A66B0` |
| 对方 PC 上一次会话（14:24） | `first_chance_av eip=0x148B66B0`、退出期 `0x148B6640` | `0x598B0000` | 两处同时命中 |

推论：

* 损坏目标的**低 16 位恒定**为桩的 RVA（`…6640` / `…66B0`），只有高位随基址变；
* 同一开机周期内 Windows 给同一加载顺序的 DLL 的基址是**固定的**
  → `EquipSlotDiagnostic.log` 里每次启动都出现同一个 `eip=…6640`，看起来"很稳定"，实为必然；
* 15:37:44 那 32 连击 `first_chance_av eip=0x198A66BC`（`operation=1` 写 `0xDF43D9B8`）
  就落在 site C 目标 `0x198A66B0` 之后：程序落进那片未映射/垃圾内存，执行若干字节后
  撞上一条写指令 → 每帧重复 → 最终在 `GR2D_DX8.DLL+0xA057`（容器析构链 `push [ebx]`）
  未被接住 → 落转储。

## 三、为什么之前漏掉了

1. 上一份诊断拿的是 14:24 的日志，当时只把 `0x148B6640` 当成"退出期补刀"，没有把
   两个 eip 联立反解基址；
2. `EquipSlotDiagnostic.log`（这份日志在 14:24 那次没拿到）里**每个会话**都有
   `eip=…6640`，是"旧构建 + 每次开机都重定位"的直接书证；
3. 结论里写死了"PC 通常落在首选基址"这一条未经验证的假设。
