## 2. 积分规则与实现要点

**核心设计：只有一个发分出口。** `end()` 是所有退出的唯一汇聚点（主动退出 / 死亡 / 掉线 / 换图 / 正常结束），
所以积分在 `end()` 里根据 `award` 标记一次性结算，避免"某条退出路径漏发或重复发"。

| 路径 | `award` 标记 | 发分 |
|---|---|---|
| 20 层全通（`finish()`） | `clear` | 40 |
| 时间耗尽（4 条超时路径） | `timeout` | `已通过层数 × 2` |
| 主动退出（`playerExit`） | 不标记 | 0 |
| 角色死亡（`playerDead`） | 不标记 | 0 |
| 掉线（`playerLeft`） | 不标记 | 0 |
| 换图离开（`changedMap`） | 不标记 | 0 |

两个必须注意的实现细节：

1. **`markClear()` 是唯一的"过层"点**，必须在这里计数。第 5/7/12/15/17 层是在 `seedPortal` 内部直接处理的，
   不走常规过层流程；只在常规流程里计数会漏掉这些层。
2. **`enterFloor()` 每层会把 `completed` 重置为 0**，所以生命期计数必须用**独立**的 `cleared` 字段，
   不能复用 `completed`，否则超时结算只会拿到"最后一层"的通过数。

## 3. 踩坑记录（重要，含一个静默失效 bug）

### 3.1 ★ `getEquipStats()` 会剥掉 `inc` 前缀，导致装备属性一行都不显示

服务端 `ItemInformationProvider.getEquipStats(int)` 的实现是：

```java
for (Data data : info.getChildren()) {
    if (data.getName().startsWith("inc")) {
        ret.put(data.getName().substring(3), DataTool.getIntConvert(data));   // incPAD -> PAD
    }
}
ret.put("reqJob", ...); ret.put("reqLevel", ...); ret.put("reqPOP", ...);
ret.put("cash", ...);   ret.put("tuc", ...);      // 这些原样入表，不剥前缀
```

**也就是说：**

- 后台管理「装备预览」读的 `catalog.json` 存的是**原始 WZ 名** `incPAD / incSTR / incPDD …`
- 而脚本里调 `getEquipStats()` 拿到的键是**剥掉前缀**的 `PAD / STR / PDD …`

两套命名。我最初照抄 catalog 的 `incPAD` 去查，结果**真机上永远查不到值**，
「基础属性」整段空白 —— 而且**不报错、不抛异常**，纯静默失败。用 mock 也测不出来，
因为 mock 是我按照自己（错误）的假设写的，返回了 `incPAD`。

- **修复**：`奖池预览.js` 的 `加成项` 全部改成去前缀名，并按奖池 1153 件**实际出现过的字段**补全到 20 个
  （`PAD/MAD/STR/DEX/INT/LUK/PDD/MDD/ACC/EVA/MHP/MMP/MHPr/MMPr/Speed/MSpeed/Jump/PVPDamage/Craft/CriticalMAXDamage`）。
- **防回归**：`test_seed_tower_rewards.py` 第 4b 节把这个契约钉死 ——
  它同时读 **Java 源码**（确认仍然剥前缀 + 取出显式入表键集合）和 **catalog.json**（取出奖池里真实出现过的
  `inc*` 字段），然后断言：① 脚本里不能有任何 `inc` 开头的键；② 奖池出现过的字段一个都不能漏展示。
  以后谁再写回 `incPAD`，测试会直接失败。
- 教训：**mock 的契约必须从实现反推，不能从自己的假设抄。**

### 3.6 背包满 → 奖品掉在地上（第二版需求）

原实现是"装备栏不够 N 格就整轮拒绝、不消耗抽奖卷"。改为**逐件判定**：

```
每次抽取：cm.canHold(id, 1)
  ├─ true  → cm.gainItem(id, 1, true, true)        进背包（随机潜能 + 获得提示）
  └─ false → 掉落地面(chr, id)                      掉在玩家脚下，自己捡
```

关键实现点（每条都对着服务端源码核过，见 `test_seed_tower_rewards.py` 第 4c 节）：

1. **`cm.canHold()` 是只读预检**（`Inventory.checkSpots`，`AbstractPlayerInteraction.java:291-301`），
   所以可以每件都先问一次，避免 `gainItem` 内部那句 `您的背包已满…` 刷满聊天框（50 连抽会刷 50 条）。
2. **掉落 API**：`chr.getMap().spawnItemDrop(chr, chr, 道具, chr.getPosition(), false, false)`
   （`MapleMap.java:2533`）。`ffa=false` → dropType 0，**归属自己**，别人捡不走；
   `playerDrop=false` → 走常规落地坐标。仓库先例：`event/SeedTower20.js:94`、`event/CafePQ_*.js`。
3. **地面装备要带随机潜能**：`gainItem` 走的是 `ii.randomizeStats((Equip) item)`，
   所以掉落前也用 `getEquipById()` + `randomizeStats()` 构造，并同样对**饰品无升级次数时补 3 次**
   （`AbstractPlayerInteraction.java:648`）。否则"掉地上的"和"进背包的"品质不一致。
4. **★ 唯一件（`info/only == 1`）会变成陷阱**：奖池 1153 件里有 **53 件**是唯一件。
   这类件如果已拥有，`gainItem` 会拒绝（`addFromDropInternal` 里 `isPickupRestricted` + `haveItemWithId`），
   **掉在地上也一样捡不起来**。所以抽取阶段就把"已拥有的唯一件"排除掉（`抽一件()`，最多重试 8 次），
   保证抽出来的每一件都真能拿到手。
5. **禁止掉落的地图**（`fieldLimit` 带 `DROP_LIMIT(0x400000)`）会把 `spawnItemDrop` 静默降级为
   `disappearingItemDrop`（奖品冒个烟就没了）。所以脚本先自查 `FieldLimit.DROP_LIMIT.check(...)`，
   落在这种图上时计入"未能发放"并在结果框说明，**不假装发成功**。
   大厅 `992000000` 的 `fieldLimit = 590316 (0x901EC)`，**不含**该位，掉落正常。
6. 抽奖卷**照常消耗**（不再有"被拒绝时抽奖卷不消耗"这条路径）；确认框在装备栏不够时会提前警告。

### 3.7 「超出背包容量的部分」掉地上 —— 抽奖与商店统一（第三版需求）

需求原话：**"只是超出背包容量的部分，改成掉落地上，消失、被人捡这种不用考虑，是正常逻辑。"**
两点含义：① 积分商店也要改（上一版只改了抽奖奖品）；② 掉落的后续命运不必特殊处理。

**实现**：把发放逻辑抽成一份**共用代码**，用生成器的标记块同时注入 `抽奖.js` 与 `积分商店.js`
（`// BEGIN 掉落兜底` … `// END 掉落兜底`，由 `seed_tower_rewards.py` 生成，两份**逐字节相同**，
契约测试会核对这一点）。公开一个入口：

```
掉落_发一个(chr, 道具ID, 随机潜能) → '包' | '地' | ''
  放得下 → cm.gainItem(道具ID, 1, 随机潜能, true)   进背包
  放不下 → 掉落_地面(...)                          掉在玩家脚下
```

| 调用方 | 随机潜能 | 与谁同口径 |
|---|---|---|
| `抽奖.js` | `true` | `cm.gainItem(id, 1, true, true)`（与百宝箱一致） |
| `积分商店.js` | `false` | 原来的 `cm.gainItem(id, qty)`（商店按基础属性发放） |

**关于"消失/被人捡不用考虑"**：这里没有做任何额外处理，用的就是常规掉落参数
`spawnItemDrop(chr, chr, 件, chr.getPosition(), false, false)`。查源码确认常规掉落 =
`dropType 0`，`MapItem.canBePickedBy` 里默认 **15 秒内只归自己**，`hasExpiredOwnershipTime()`
（`SECONDS.toMillis(15)`）之后 `isFFADrop()` 变 true ⇒ **谁都能捡**；到期自然消失。
也就是说"被人捡"本来就是默认行为，脚本不需要也不应该干预。
（上一版说明里写的"归属自己、别人捡不走"是**不准确**的，只有前 15 秒。）

**商店的语义**：积分按**整笔**扣除（买 5 张就扣 800 分），放不下的部分掉在地上由玩家自己捡。
原来那条"背包空间不足，请先清理 → 拒绝购买"整块删掉了；确认框改成提前警告。
`fieldLimit` 禁掉落的地图上，掉不出去的部分如实记为"未能发放"（**不退款**——需求是只改掉落，
积分口径不动；而且商店只能从大厅 NPC 进入，`wz/Map.wz` 里 `2540000` 只出现在
`Map/Map9/992000000.img.xml`，该图允许掉落，所以这条路径实际上是理论分支）。

**生成器顺带修的两个隐患**（都是多标记块才暴露的）：

1. `script_block()` 原来每次都从**磁盘**读原文，同一文件写第二个块时会把第一个块的填充**回滚**。
   改为优先基于 `self.outputs` 里的待写内容。
2. `install()` 的"块外内容未被改动"守卫只屏蔽一个标记块，导致"另一个块被填充"被误判成
   "块外被改动"。改为 `mask_blocks()` 一次性屏蔽该文件的**全部**标记块。
   ⚠️ 同时更正了这个守卫的**真实能力**：它证明不了"没人手改块外"（块外改动会被原样带进新内容，
   这是有意的），它拦的是**标记丢失/重复**和**切分错位**。已把注释改成准确表述。

**已知取舍（需你确认）**：商店的法弗纳仍是**基础属性**发放（沿用原来的 `gainItem(id, qty)`，
即 `randomStats=false`），而抽奖奖池走 `randomizeStats`（每条已有属性 +0~5）。这是原有行为，
本次没有改动；如果希望商店也带随机潜能，说一声即可。

## 7. UI 修复（2026-09-30 第二轮）

反馈原话：「奖池预览的排练（排列）不整齐，而且没名称，鼠标移上去也没有装备详情，商店的也没有详情」。

### 7.1 根因

| 现象 | 根因 |
|---|---|
| 悬停不弹装备说明 | `#v`（可交互图标）被 `#L<序号>#...#l` 包住。链接会在客户端生成一块可点击区域并**接管鼠标**，里面的图标收不到悬停事件。**不报错**，只表现为"鼠标移上去没反应"。 |
| 排列不整齐 | ① 8 列图标网格靠空格分隔，图标像素宽与空格字宽不成整数倍，逐格累积误差；② 商店菜单用 `\t` 对齐 —— 对话框**没有制表位**，`\t` 必然错位。 |
| 没有名称 | 网格只渲染了图标，没放 `#t`。 |

`#i` 与 `#v` 的语义出处：TMS-248 的 `resources/npcFormatting.txt` ——
`#i[id]#` = Item image（静态），`#v[id]#` = **Item image (interactive)**。

### 7.2 改法

**奖池预览**：网格 → **每行一件的清单**（每页 20 件）。图标在链接外、名称在链接内，拆成两段：

```
#v<道具ID># #L<序号>#<序号>  #t<道具ID>##l
```

> 为什么不做「网格 + 名称」：图标是位图（像素宽）、名称是文字（半角宽），两种单位不同，
> 列首无法精确对齐。一行一件才能保证绝对整齐、且名称不被截断。

**积分商店**：`#i` → `#v` 并挪到链接外；去掉 `\t`，价格用半角宽度左补空格右对齐；
选中装备后**新增属性概览**（需求一行 + 加成一行）。

**共用「装备属性」标记块**：属性读取与宽度工具抽成 `// BEGIN 装备属性` 块，由生成器同时注入
`奖池预览.js` 与 `积分商店.js`，**两份逐字节相同**。理由同「掉落兜底」：`getEquipStats()` 剥
`inc` 前缀这件事，两边写法只要差一点，就会一边正常、一边整段空白且不报错。

### 7.3 验证

- 契约测试 `test_seed_tower_rewards.py` 新增 **4d 节**：两份属性块逐字节相同；
  源码里 `#v` 必须是「链接外」的拼接形态；商店菜单不得出现 `\t`。
- 新增流程测试 `test_seed_tower_rewards_flow.js`（Node + mock `cm`，**144 项全绿**）：
  真正把脚本跑起来，对**渲染出来的文本**断言 —— 包含"本页 20 个 `#v` 全部落在
  `#L...#l` 之外"这一条（Python 静态检查做不到）。

### 7.4 生成器健壮性

`tickets()` 改为**幂等跳过**：5 件道具与名称都已在位时整段跳过，**不再读 `ICON_SOURCE`**。
图标源（`~/Downloads/5157420.png`）是用户临时提供的、随时会被清掉，而图标早已编码进

## 8. 抽取口径改为「同一批连抽内不重复」（2026-09-30 第三轮）

### 8.1 原来的口径确实不符合要求

要求是「在奖池中随机抽，不重复」。核查后确认**原实现是「有放回」**：

```js
var id = 池[Math.floor(Math.random() * 池.length)];   // 每次独立、等概率、抽完放回
```

这和本服百宝箱是同一口径（`GachaponService.java:276` 的 `Randomizer.nextInt(poolRewards.size())`），
不是 bug，但重复率比直觉高得多（N=1153）：

| 连抽 | 至少出现一件重复 |
|---|---|
| 5 | 0.9% |
| 10 | 3.8% |
| 20 | 15.3% |
| 50 | **66.0%**（期望 1.06 对） |

奖池**数据本身零重复**（1153 件去重后仍是 1153，无跨类重复 ID）。唯一件（`info/only==1`，53 件）
原本已有排除，其余 1100 件没有任何重复保护。

### 8.2 改法：建候选池 → 等概率取 → 取走即移除

```js
var 候选 = 候选池(chr);   // 奖池的一次性副本，建池时剔掉「已拥有的唯一件」
var id = 抽一件(候选);    // 等概率取下标；取完用「尾元素补位 + pop」移除，O(1)
```

### 8.3 ★ 关键取舍：排除动作必须在**建池时**做，不能放抽取循环里重试

旧结构是「循环内重试最多 8 次，跳过已拥有的唯一件」。照搬它去加「跳过已抽到的」会随收集进度
指数级恶化 —— 单次命中可用件 = 剩余/1153，8 次全落空就是**卷照扣、什么都没给**：

| 已收集 | 单次命中可用件 | 8 次重试全失败 |
|---|---|---|
| 500 | 56.6% | 0.13% |
| 1000 | 13.3% | **31.9%** |
| 1100 | 4.6% | **68.6%** |

先筛后抽没有这个问题：本批最多 50 次，候选常年 1100 件以上，抽不干
（`抽一件` 返回 `null` 的唯一条件是候选池被抽干）。

候选池**必须是副本** —— 原地删 `奖池()` 返回的平铺缓存会把它抽空，下一批就没奖可抽。

### 8.4 边界与**没做**的部分

- **跨批不保证**：换一张卷再抽，仍可能抽到上一批抽过的件。这是拍板过的口径（「单次连抽内不重复」）。
- **没做「角色永久不重复」**：奖池 1153 件、单张卷最多 50 次，做永久不重复必须落库收集进度。
  硬约束：`extend_value` 是 `varchar(255)`（219 个迁移里无 ALTER），1153 位位图
  **hex 编码 289 字符放不下**，Base64（145 字节 → 196 字符）才刚好；且需额外定义
  「集齐 1153 件之后」的行为（不扣卷 / 退卷 / 保底）。
- **掉在地上那部分同样不重复**：件数按「结果」算，落地件也占用本批名额。

### 8.5 验证

- 契约测试新增 **4d 节**（静态）：候选池必须是副本（禁止 `源.pop/splice/shift/unshift/reverse/sort/length=`）、
  取一件必须真的移出候选池、不得退回 `池[Math.floor(Math.random()*池.length)]` 的有放回写法、
  唯一件排除只允许出现在建池函数体内。
- 流程测试新增 6 组（行为）：50 连抽去重后仍是 50、结果面板不再出现 `×N`、
  背包满时落地的 50 件也互不重复、连抽两批后 `奖池()` 仍是 1153 件（证明用的是副本）、
  `抽一件` 取完返回 `null`。
- **反向验证**：对 3 种回归（退回有放回 / 原地删奖池 / 取消移除）逐一注入，契约测试全部拦下；
  其中「原地删」在**重跑生成器刷新清单哈希之后**仍被专用断言拦下，证明它不是靠哈希兜底。
