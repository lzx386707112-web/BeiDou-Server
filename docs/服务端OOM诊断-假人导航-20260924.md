# 服务端 OOM 诊断：假人导航系统（2026-09-24 14:42–14:48）

## 一句话结论

日志里唯一的根因是 **`java.lang.OutOfMemoryError: Java heap space`（4GB 堆被吃满）**，
内存黑洞在**假人导航系统**：`SearchState` 与 `GraphCacheKey` 两个反编译重建类丢了值语义的
`equals/hashCode`（退化成 `identityHashCode` / `this == o`），
分别造成「单次寻路状态爆炸」和「导航图缓存永不命中 + 静态缓存无上限增长」。
其余报错（封包处理器、`Error in scheduled task`、`Error saving chr ... SQLException`）都是堆耗尽后的连带现象。

## 已实施修复（2026-09-24 15:00）

### 关键补充：扳机是 `refreshMovementProfile`

`BotMovementManager.refreshMovementProfile` 里有一句

```java
BotMovementProfile updated = BotMovementProfile.fromCharacter(entry.bot);
if (updated.equals(entry.movementProfile)) return false;   // ← identity 比较，恒为 false
```

`updated` 每次都是新建对象，identity 比较永远不成立，于是**每一次刷新都判定"移动属性变了"**：

- `clearNavigationState(entry)` → 假人的寻路计划被反复丢弃 → 不停重新寻路（对应日志里的频繁 Slow pathfind）；
- `peekGraph(map, updated) == null` 恒成立 → 每次 `warmGraphAsync` 都发起一次**整图重建**，
  并把新键 + 新图永久塞进 `GRAPHS`。

所以 `BotMovementProfile` 的 identity 语义是让上面两个缺陷**高频触发**的扳机，必须一起修。

### 遗留与扫描脚本（含一次翻车记录）

**先说踩过的坑**：第一版扫描脚本把统计写在 `for p, lines in files.items(): ... if cls in usage_re: continue` 里，
结果每个类只在"第一个被遍历到的文件"里统计了一次，后面全部 `continue` 跳过 → 所有类都报 0 命中。
据此我一度得出"剩余桩都没被当键用"的**错误结论**，并且差点漏掉 `JumpLandingKey` / `RopeGrabKey`。
教训：**统计必须跨整棵树做**，分级要区分「Map 键位 `<C,`」和「集合元素位 `<C>`」，不能用 `[<,]\s*C\s*[>,]` 混在一起。

修完 5 个类后，剩余 `System.identityHashCode(this)` 桩：**31 个类 / 33 处**
（GCMoveSystem 27 处 + BotTownSystem 6 处，其中 `Claim` 在两个文件里各一处）。
逐个人工确认后的结论：

- **Map 键位（`<C,`）：0 处** —— 所有当键用的同一性桩已清零（这正是引爆 OOM 的那一类）。
- **集合元素位（`<C>`）**：10 个类出现在 `List<...>` 或 `ThreadLocal<...>` 里
  （`Anchor` `ClassifiedLoop` `ClosedLoop` `JumpRegionProfile` `Ledge` `MapShare` `TaxiEdge`
  `TownEntry` `WalkRegionLookup` `Zone`）。`List` 不调 `contains/indexOf/remove` 就不会走 `equals`；
  已全包 grep 复核，这些集合上的同类调用只有 `Integer` 键（如 `ACTIVE.remove(Integer.valueOf(botId))`）
  和 `Zone.contains(x, y)`（自定义坐标判断），**没有一处依赖这些类的 `equals`**。
- **`equals` 业务判断**：全 `ArtificialPlayer` 包内唯一一处是已修的
  `BotMovementManager.refreshMovementProfile` 里的 `updated.equals(entry.movementProfile)`。

所以：剩下的桩只影响调试可读性（`toString()` 全返回类名），不影响正确性与内存。
若后续再重建 `asm-bot-mini.jar` 里的新类，重跑下面这段确认即可。

```python
# 找出所有 identity 桩类，并按「Map 键位 <C,」/「集合元素位 <C>」分级
# 用法：在仓库根目录执行；统计必须跨整棵树（勿只在定义文件内统计）
import os, re
ROOT = "gms-server/src/main/java/soloMapling"
CLS_RE = re.compile(r"^(\s*)(?:[\w$.<>,?\[\]\s]*?)\b(class|record|enum|interface)\s+([\w$]+)")
STUB_RE = re.compile(r"System\.identityHashCode\(this\)")

files = {}
for dp, _d, ns in os.walk(ROOT):
    for n in ns:
        if n.endswith(".java"):
            p = os.path.join(dp, n)
            files[p] = open(p, encoding="utf-8", errors="replace").read().splitlines()

decls = {p: [(i, len(m.group(1)), m.group(3)) for i, l in enumerate(ls, 1)
             if (m := CLS_RE.match(l))] for p, ls in files.items()}

stubs = []
for p, ls in files.items():
    for i, l in enumerate(ls, 1):
        if STUB_RE.search(l):
            ind = len(l) - len(l.lstrip())
            cand = [d for d in decls[p] if d[0] < i and d[1] < ind]
            stubs.append((p, i, max(cand, key=lambda d: d[0])[2] if cand else "?"))

alltext = "\n".join(l for ls in files.values() for l in ls)
seen = {}
for p, i, c in stubs:
    seen.setdefault(c, []).append((p.split("/soloMapling/")[-1], i))

print(f"identity 桩类 {len(seen)} 个 / {len(stubs)} 处")
risky = []
for c, locs in sorted(seen.items()):
    key = len(re.findall(r"<\s*" + re.escape(c) + r"\s*,", alltext))   # Map 键位
    ele = len(re.findall(r"<\s*" + re.escape(c) + r"\s*>", alltext))   # 集合元素位
    if key or ele:
        risky.append(c)
        print(f"  {c:<24} 键位={key:<3} 元素位={ele:<3} {locs[0][0]}:{locs[0][1]}")
print("需要人工确认:", risky if risky else "无")
```

> 变量形式的比较（`updated.equals(entry.movementProfile)`）和
> 集合变量上的 `contains/indexOf/remove`（如 `anchors.contains(a)`）。
> 本次两者都已手动过了一遍，见上文结论。

> 说明：该判断只看「类型参数位置」。变量形式的比较（如 `updated.equals(entry.movementProfile)`）

| 事实 | 证据 |

| 服务端**不在**开发用的 Mac 上 | 本机无 java 服务进程、全盘无 `BeiDou*.jar`、无 `gms-server/cache/bot-nav`、8686/19696 无监听 |

在 6 GB 机器上允许堆涨到 6 GB，等于把 Windows + MySQL + 客户端一起推进磁盘交换（**顺带解释上次为何 7 分钟就 OOM：默认堆只有 6144/4 = 1.5 GB**）。整机变慢后，假人的 250 ms 调度被拖成秒级 → 表现为"很少 / 不动 / 不说话"。

**教训：给 JVM 定堆要按服务端那台机器的物理内存，不要按开发机（16 GB）。**

### ② `GRAPHS` 容量兜底写成了整表清空（逻辑错误）

15:00 那版写了：

```java

}
```

键空间 = 地图数 × 移动属性组合数，很容易超过 128。一旦超过：

1. 每次 `put` 都把整张表清空 → 命中率归零 → 每次 `getGraph` 都重建（`warmGraphAsync` 的 `containsKey` 守卫也失效，反复提交重建任务）；
2. **`peekGraph(map)` / `peekClosestGraph` 这类按 mapId 的"容错查询"常年拿到 null** —— 它们原本靠"条目只增不减"总能捞到一张图。受影响的正是：
   - `BotPhysicsEngine.resolveWalkRegionLookup`（行走区域查询，物理层，每个运动 tick 都要）；
   - `GCMovementDriver.tryCoarseAdvance` → `peekBestGraph`（非活跃地图的粗粒度推进）。

## 顺带记录：本次值语义修复带来的一个**行为翻转**（预期内）

`BotNavigationManager.tryExecuteJump` 里有一道"图是否已预热"的身份门：

identity 键时代 `peekGraph(map, profile)` 恒为 null → 这个门恒真 → **跳跃分支等于死代码**。修好值语义后门才开始放行，`tryExecuteJump` 第一次真正执行。这是设计意图（门本来就是"图热了才跳"），但意味着**假人的跳跃行为是本次才真正启用的**；观察重启后的表现时要把这一点算进去。同类还有 `BotMovementManager.adjustGrindingTargetPosition`（现在才会把打怪目标夹到当前区域的安全带内）。

## 排查方法备忘（下次"改完就坏"怎么定位）

1. 先确认**改动会在哪台机器上生效**，以及那台机器的资源（本例：6 GB / 同机 MySQL+客户端）。开发机与服务端机器不是一台时，这条最容易被漏掉。
2. 逐条列出改动造成的**语义翻转**（miss→hit、null→非 null、死代码→活代码），而不是只看"新代码对不对"。
3. 特别警惕"原来那个 bug 是被依赖的"：`clear()` 让容错查询失明就是这一类；`peek*` 系列一旦从"总能拿到"变成"常年 null"，受伤的是物理层和粗粒度导航。
