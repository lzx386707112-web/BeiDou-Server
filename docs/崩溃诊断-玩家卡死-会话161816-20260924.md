### 2.1 window-lost 转储的线程现场（关键）

- 26 个线程；**无 Exception 流**。
- `tid=12500`（主线程）：`eip = nvd3dum.dll+0x3B4C0` → 阻塞在 **NVIDIA D3D 用户态驱动**里。
- 其余 25 个线程：全部停在 `ntdll.dll`（`NtWaitForSingleObject` / `NtWaitForMultipleObjects` 一类系统调用桩）→ 都在等。
- 主线程是**唯一在跑的线程**，且不在 exe 代码里 —— 这就是"卡死"的现场。

### 2.2 `_com_error` 的抛出位置（本次新发现）

异常记录 `i0=0x19930520`（MSVC EH 魔数）`i2=0x00b44b18` → `_ThrowInfo` → 可捕获类型 `.?AV_com_error@@`。
`address=76C00F22 = KERNELBASE!RaiseException`，栈候选里反复出现两个 **`BeiDou.exe` 地址**：

- `BeiDou.exe+0x00003119` @ `00403119`
- `BeiDou.exe+0x0000316f` @ `0040316F`

反汇编（`clien/BeiDou.exe`，固定 `ImageBase=0x400000`）：

```
00403114: e8 4d 00 00 00        call   0x403166          ; ← 调用者
00403119: 83 65 fc 00           andl   $0x0,-0x4(%ebp)   ; ← 返回地址（出现在栈上）
...
00403166: 56                    push   %esi
00403167: 8b f1                 mov    %ecx,%esi
00403169: ff 15 d0 c9 bd 00     call   *0xbdc9d0         ; fn(ecx)   ← 异常从这里抛出来
0040316f: 85 c0                 test   %eax,%eax         ; ← 也出现在栈上
00403171: 74 16                 je     0x403189          ; fn()==0 → 退出循环
00403173: 8b ce                 mov    %esi,%ecx         ; loop:
00403175: ff 15 d0 c9 bd 00     call   *0xbdc9d0         ; fn()
0040317b: 85 c0                 test   %eax,%eax
0040317d: 74 0a                 je     0x403189
0040317f: 6a 00                 push   $0x0
00403181: ff 15 f4 02 bf 00     call   *0xbf02f4         ; <单参数例程>(0)，疑似 Sleep(0)
00403187: eb ea                 jmp    0x403173          ; ← 无迭代上限、无超时
00403189: 5e                    pop    %esi
0040318a: c3                    ret
```

**这是一段没有迭代上限、没有超时的等待循环**：`while (fn(x) != 0) { <让出>(0); }`。
`0x403114` 的调用者做 `movl $0x40 / $0x20`、`(x+3)&~3` 对齐、`HeapAlloc` 型调用与 `[edi+esi*4+0xC]` 索引 → 是一个**指针数组/容器扩容**例程。

`0xBDC9D0` 与 `0xBF02F4` 都位于 `.data`（`0xBD7000–0xBF9000`），**不在导入表里** → 是运行时赋值的函数指针（该 exe 大量使用手工解析的 API 指针）。因此：

- 异常是从 **`0xBDC9D0` 指向的那个例程内部**抛出来的，不是 exe 里某个固定地址 —— **所以它没法像 P1–P4 那样用"改一个站点"的方式补掉**。
- 现有 4 个补丁点（`0x403AE9` / `0x410FF5` / `0x401D3E` / `0x401D52`）**都不覆盖这条路径**。

### 2.3 9 次 `_com_error` 的性质

- `code=0xe06d7363`、类型 `.?AV_com_error@@`、`ebx=0x80004002` = **E_NOINTERFACE**（注意：与历史上见过的 `0x80030002` STG_E_FILENOTFOUND 不是同一个）。
- 都是 **first-chance**，日志里没有任何"未处理异常 / crash"事件 → 它们**被客户端自己 catch 掉了**，属于媒体/Flash 探测失败的噪声，而不是致命错误。

### 2.4 Flash 侧状态（两实例一致）

```
pid14780: flash_slot=1F42E088 flash_movie=00000000 flash_null_skips=0
pid14732: flash_slot=1CE8E088 flash_movie=00000000 flash_null_skips=0
```

- `flash_slot` 的地址解码正确（= `WzFlashRenderer` 基址 + `0x6E088`），说明**守卫和槽位逻辑工作正常**。
- `flash_movie` **全程为 0** → **Flash 影片从未挂上去过**。
- `flash_null_skips=0` → 守卫一次都没被迫跳过（不是"守卫兜住空影片"那种"不崩但不显示"的战斗场景）。
- `last_resource="(none)"` → 整个会话没有通过被钩的 API 打开过新的 WZ 资源。

即：**客户端停在"Flash 媒体始终没能就绪"的状态**，这与第 4 节"要补资源本体"的既有结论一致。

## 5. 根因判断（按置信度分层）

**已证实**
1. 本次不是崩溃：0 AV、无 Exception 流、`ExitProcess(0)`。既往的"重定位僵尸条目"崩溃**已修复并在本机复现验证**（4 连 0）。
2. 窗口消失的瞬间，主线程阻塞在 **`nvd3dum.dll`**（显示驱动）内部，其余线程全部空等 → **图形路径阻塞**导致"卡死"观感。
3. 该会话存在 9 次被吞掉的 `_com_error`(E_NOINTERFACE)，抛出点在 `0x403166` 这个**无上限等待循环**所驱动的动态例程里。
4. 主线程在窗口消失前后把 `WzFlashRenderer.dll` **反复 load 57 次**、基址恒定（同一地址重映射）→ 存在 **DLL load/unload 抖动**。
5. Flash 影片全程为 NULL，即 **Flash 媒体从来没就绪**。
6. 玩家跑的 `BeiDouSetItemCompat.dll` **不是仓库当前版本**（差一次称号档位修复）。

**推断（待证）**
7. 最可能的机理：**Flash/媒体渲染器在"销毁—重建"过程中失败**（E_NOINTERFACE），主线程随之卡在显示驱动里；窗口已被销毁且未重建，客户端最终走完收尾并 `ExitProcess(0)`。玩家看到的就是"画面卡住 / 窗口没了 / 游戏自己关了"。
8. `0xBF02F4` 那个"单参数、传 0"的调用**疑似 `Sleep(0)`**，即该循环是**忙等**（CPU 132% 与"忙等"相符）。需确认后才能按此下补丁。

**未解释**
9. 是"玩家看到卡死后自己关掉窗口"还是"客户端自行销毁窗口"—— 日志里没有 WM_CLOSE / DestroyWindow 事件，两种都无法排除。**下次复现请开第 7 节的观测点。**

## 6. 修复方案

### P0 立即执行（零二进制风险）

1. **重新交付整套客户端**，用仓库当前 `clien/` 构建；重点确认 `BeiDouSetItemCompat.dll` = `0x000147E6`（20480 字节）。
   - 交付包必须**给全并附清单**（漏一个兼容 DLL 就断链，已实证）。
   - 附 `sha256` + PE `CheckSum` 清单和校验脚本。
   - **等长替换是最高危情形**：交付后务必让玩家用 `certutil -hashfile <path> SHA256` 与 Mac 端 `shasum -a 256` 逐项核对；不一致就 `del` + 重新 `copy`（或重启虚拟机），不要覆盖式复制。
2. **单实例纪律**：启动前确认没有残留 `BeiDou.exe`；客户端放在**普通目录**运行，不要从 `.zip` 里直接启动。
3. 收集复现时的**两处观测**（`tool/client-debug/wz-file-logger-fix/README.md` 第五节）：`event=message_box` / `event=error_dialog`，以及 `clien/beidou_wz_access.log` —— 用来区分"玩家关窗"与"客户端自毁"，并定位缺失的媒体/Flash 路径。

### P1 二进制修复（必须走生成器 + 契约测试，禁止叠加）

4. **给 `0x403166` 的等待循环加界限 / 降忙等**
   - 最小改动：`0x40317F` 的 `6a 00`（`push 0`）→ `6a 01`（`push 1`）。**等长、无重排、不动 `.reloc`**，把忙等降为 1 ms 粒度让出。
   - 注意：这只解决"空转烧 CPU"，**不解决"等不到"**。真正的修法是给循环加**迭代上限 + 超时**，超时后走"跳过该媒体/Flash 元素"的降级路径。
5. **消除 `WzFlashRenderer.dll` 的 load/unload 抖动**
   - 现状：包装层（`WzFileLogger.dll`）在每次 Re-render/Release 时重新 `LoadLibrary("WzFlashRenderer.dll")`，57 次/600 ms，基址不变 = 反复卸载再映射。
   - 应改成"**加载一次、全程持有引用**"，绝不在每次调用时 load+free。这也是让 flash 守卫的基址校验保持有效的必要前提。
6. **补齐 Flash/媒体资源本体**
   - E_NOINTERFACE 和历史上的 `0x80030002`(STG_E_FILENOTFOUND) 都指向同一个遗留项：**缺的是资源/接口本身**，补丁只是让失败不再崩。`flash_movie=00000000` 全程为 NULL 就是它的直接后果。
7. 关于"第 5 个 `_com_error` 抛出点"：**不能**按 P1–P4 的站点补丁方式处理 —— 异常从动态解析的例程内部抛出（见 §2.2）。正确做法是在 §2.2 那个 `call *0xBDC9D0` 的**包装层**捕获 `_com_error`，或先弄清 `0xBDC9D0` 指向谁再决定。

### P2 流程纪律

8. 任何补丁落地后：**全量**跑 `fix_dll_reloc_hygiene.py clien/*.dll`；契约测试要有"`type==3` 条目不得落在打补丁的 `rel32` 区间"断言；交付包写明修复前后 CheckSum/sha256。
9. **改完不发＝没修**（本次第 6 项版本差就是这条纪律的现成反例）。

3. 判"跑的是哪版"：`which_build.py <dmp> --dll-dir clien`；或读转储 `MINIDUMP_MODULE.CheckSum`(+12)。
