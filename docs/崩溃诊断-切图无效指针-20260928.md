## 一、结论速览

| 问题 | 结论 |
| --- | --- |
| 「无效指针」是什么？ | **HRESULT `0x80004003` = `E_POINTER`**（十进制 `-2147467261`）。不是访问违例，是 MSVC COM 的 `_com_error`（异常码 `0xE06D7363`） |
| 是不是真崩溃（AV）？ | **不是**。全程没有 `first_chance_av`、没有 `0xC0000005`、`window-lost` / `exit-process` 转储里都没有异常流 |
| 客户端怎么结束的？ | **自行走正常收尾路径退出**（`nst*.tmp` 探测 → 资源批量释放 → `ExitProcess` 钩子写转储 → 窗口消失） |
| 抛点在哪？ | `BeiDou.exe+0x402643`：`push $0x80004003` → `call 0xA5FDE4`（`_com_issue_error`） |
| 谁调的？ | `BeiDou.exe+0x5CADAC`，媒体/资源 COM 包装函数，**同一个函数在 `+0x5CACFB` 调用被 P1 补丁改过的创建包装 `0x403A93`** |
| 直接机制 | **一个 COM 接口槽是 NULL，却被当成有效对象取用**；抛它的 `0x40263B` 就是一个「空则抛 `E_POINTER`」的访问器 |
| 上游成因 | 媒体/视频子系统本次**从未就绪**（D3D8 设备未挂载，Flash 影片槽自始至终为 NULL）；另有 `BeiDouWeatherCompat.dll` 因 `enableWeatherSystem=false` 未加载 |
| 和 P1 补丁的关系 | **P1（`0x403AE9` `7D`→`EB`）把「创建时抛错」变成了「使用时抛 `E_POINTER`」** ——正是"改了一处、在另一处冒出来"的典型 |

## 三、调用链（逐跳反汇编确证）

xtajit 环境下所有线程的 `CONTEXT.Eip` 都读成常量 `0x10002`（仿真产物），EBP 链在异常现场也立刻断。
本链条是用**「栈上的值 + 它前面那条 `call` 指令」**逐跳验证出来的——
每一跳的返回地址就是下一跳里那条 `call` 的下一条指令，且栈地址单调上升：

```
KERNELBASE!RaiseException            @0x75589E4F        ← eip=0x75589E4F, code=0xE06D7363
  ↑ return site 0xA60BEB  ←  call *[0x00AF0130]  @0xA60BE5      (.data 运行时指针，间接调 RaiseException)
  ↑ return site 0xA605E7  ←  call 0xA60BB7       @0xA605E2      (在 _com_raise_error 体内)
  ↑ return site 0xA5FDEF  ←  call 0xA605C3       @0xA5FDEA      0xA605DC: push $0xB44B18 (pThrowInfo)
  ↑ return site 0x40264D  ←  call 0xA5FDE4       @0x402648      ★ _com_issue_error
  ↑ return site 0x5CADB1  ←  call 0x40263B       @0x5CADAC      ★ 媒体/资源 COM 包装
```

### 抛点本体：`0x40263B` 是一个「空则抛 E_POINTER」的访问器

```asm
0040263b  push %esi
0040263c  mov  %ecx,%esi
0040263e  cmpl $0x0,(%esi)          ; ← 检查 *esi
00402641  jne  0x40264d             ; 非空 -> 正常返回
00402643  push $0x80004003          ; ★★★ E_POINTER = 「无效指针」
00402648  call 0xa5fde4             ; _com_issue_error(0x80004003)
0040264d  mov  (%esi),%eax
0040264f  pop  %esi
00402650  ret
```

### 调用者：`0x5CACxx` 媒体/资源 COM 包装（同一函数里的两处关键点）

```asm
005cacfb  call 0x403a93   ; ★ 被 P1 补丁改过的 CreateInstance 包装（0x403AE9: 7D→EB）
005cad00  mov  %eax,%ecx
005cad06  call 0x4032b2   ; 16 字节 variant -> 接口指针
005cad0b  cmp  %ebx,%eax  ; ebx == 0（空值测试）
005cad0d  mov  %eax,-0x68(%ebp)
005cad10  mov  %ebx,-0x64(%ebp)
005cad13  je   0x5cad36   ; 空 -> 走失败分支
...
005cad25  mov  $0x80004002,%ebx        ; E_NOINTERFACE（失败分支 A）
005cad2f  call 0xa5fde4                ; ← 也会抛
005cad36  mov  $0x80004002,%ebx        ; E_NOINTERFACE（失败分支 B）
...
005cadac  call 0x40263b   ; ★ 走到这里，槽还是 NULL -> 抛 _com_error(E_POINTER)
```

### 转储里的直接物证

`first-chance-cpp-20260928-082915-pid6112-30283171.dmp` 的异常流：
`code=0xE06D7363` `params=['0x19930520','0x1adb04','0xb44b18']`（MSVC C++ throw 的标准三参数：
魔法数 / pExceptionObject / pThrowInfo）。异常对象 `0x001ADB04` 的原始字节：

```
0x001ADB04  40 12 b4 00 | 03 40 00 80 | 00 00 00 00 | 00 00 00 00
            ^^^^^^^^^^^  ^^^^^^^^^^^
            vtable        m_hr
            BeiDou.exe+0x741240   0x80004003 = E_POINTER ← 「无效指针」
```

**这是「无效指针」四个字的直接来源**，不需要任何推断。

### 日志里 `ebx = 0x80004002` 是控制流路标，不是干扰项

32 次异常中 `ebx` 有两种取值：`0x80004002`（22 次）与 `0x0e4a7ea8`（10 次）。
`0x80004002` 恰好就是上面 `0x5CAD25` / `0x5CAD36` 写入的常量 ——
它证明执行**确实经过了失败分支**。所以「无效指针」与「E_NOINTERFACE」是同一条失败路径上、
不同位置写下的两个值，不要按两个独立故障去追。

## 四、为什么 P1 补丁没能拦住它

`tool/client-debug/beidou-skip-media-com-error/README.md` 的修法是
`0x403AE9`：`7D 0C`(`jge`) → `EB 0C`(`jmp`)，让**创建失败不再抛**、沿调用链降级。

**该补丁当前已生效**：

```
00403ae7  85 c0        test %eax,%eax
00403ae9  eb 0c        jmp  0x403af7      ← 已是 EB（补丁后）
00403aeb  68 18 83 bd 00  push $0xbd8318  ← 死代码，保留
```

但同一个函数后面还有**第二处**对同一个槽的取用（`0x5CADAC`）。
于是失败只是**换了地方冒出来**：

```
补丁前：创建失败 → 0x403AF2 抛 _com_error(hr = 0x80030002 STG_E_FILENOTFOUND / 0x80004002)
补丁后：创建失败 → 静默，槽保持 NULL → 0x402648 抛 _com_error(m_hr = 0x80004003 E_POINTER)
```

这正是你担心的「改了一个地方又触发其他崩溃」——而且**它已经发生过了**。
`beidou-skip-media-com-error/README.md` 里「走 0x5cad36 起的正常清理，**全程不再 throw**」
这句结论在本路径上不成立：`0x5cad36` 之后代码继续往下走到 `0x5cadac`，那里会抛。

> 补充：`0x5CADAC` 读的 `-0x64(%ebp)` 与 `0x5CAD0D/0x5CAD10` 写入的槽位是否严格同一个对象，
> 是本文档**唯一未用反汇编彻底钉死**的一环（见第七节）。

## 六、澄清两点（避免误判）

1. **本次不是访问违例崩溃。**
   - 会话日志里 `C0000005` / `access_violation` / `first_chance_av` / `event=crash` 命中数为 **1**，
     那 1 处只是 `seq=2` 的过滤声明行（`filters=C0000005/...`）。
   - `window-lost` 与 `exit-process` 两个转储**都没有异常流**。
   - `exit-process` 转储主线程（tid `0x2550`）正停在 `dbgcore.dll+0x22F0`，
     即**正在执行 `MiniDumpWriteDump`** —— 是 `ExitProcess` 钩子在写转储，属于受控退出。
   - 退出期模块从 111 个减到 106 个（`WzFlashRenderer` / `PCOM` / `ResMan` / `SOUND_DX8` /
     `prl_umdd` / `msvcp71` / `msvcr71` 被卸载），是正常收尾顺序。

2. **`flash_movie=0x00000000` 是 NULL，不是野指针。**
   说明 WzFileLogger 的 flash 槽位野指针修复（`tool/client-debug/wz-file-logger-fix/`）已生效；
   本次不是那条老问题复发。

## 七、唯一还没钉死的一环

**08:33:09.841 那次「未处理异常」的具体类型没被记录下来。**

原因是诊断层的 `cpp_limit=32` 在 08:31:13 就被 32 次 `_com_error` 用光了，
之后任何 first-chance C++ 异常都不再记录，而 08:33:09 只有一条
`exception_filter action=preserved_client_filter`（该分支不记异常详情）。
`window_lost` / `exit-process` 转储也不含异常流，所以这一次确实没有物证。

因此有两种读法，本文档不替你选：

- **(a)** 08:30:33–08:31:13 那 32 次 `E_POINTER` 中某次弹了框，你在 08:33 前后关掉了客户端；
  08:33:09 的异常只是退出过程中的副作用。
- **(b)** 08:33:09 发生了一次新的未处理异常，直接导致客户端结束。

两者都以同一条「媒体/资源接口为 NULL」为底。**要区分，只需把
`beidou_diagnostics.ini` 里的 `cpp_limit` 调大（或临时停用诊断器）后复现一次。**

## 八、建议的下一步（先验证，再动手）

按"最小证据化改动"的原则，建议顺序如下，**每一步都不改二进制**：

1. **复现并留下证据**
   把 `cpp_limit` 调大（如 256）后重进同一个图，确认：
   - 是否仍抛 `E_POINTER`；
   - `E_POINTER` 是发生在**进图瞬间**还是**一段时间后**；
   - 错误框弹出时日志里最后一条 `resource_open` / `first_chance_cpp` 是什么。
2. **证伪/证实天气开关**
   临时把 `config.ini` 的 `enableWeatherSystem` 改成 `true`（允许加载
   `BeiDouWeatherCompat.dll`）后重试。若「无效指针」消失 → 直接锁定提供者缺失；
   若不变 → 排除该假设，回到 D3D8 那条链。
3. **先修上游，别先补下游**
   `docs/MCV视频不播放诊断-20260928.md` 第五节已给方案（让设备捕获不再依赖 Gr2D 的
   `GetProcAddress` 槽）。上游设备一旦挂上，`0x5CADAC` 处的槽就不会是 NULL，
   「无效指针」应当随之消失——比再给 `0x5CADAC` 打一个站点式补丁更根本。
4. **如果最终仍要给 `0x5CADAC` 打补丁**
   那是**第四处** COM 抛点。必须走 `beidou-unified-patch` 从
   `backup/BeiDou.exe.orig` 全量重建，**禁止在现有二进制上叠加**；
   并同步巡检 `.reloc`，避免重定位僵尸条目。

> ⚠️ 提醒：`beidou-unified-patch` 的 P1 已经证明了"只压抛点不改上游"会换个地方冒出来。
> 在这一轮把上游（D3D8 / 接口提供者）理清之前，**不建议再往 `BeiDou.exe` 上加抛点补丁**。

> 📌 **本条已被第十节的 P5 方案取代（不是推翻，是换了做法）**：P5 没有再去"压抛点"，
> 而是先用全局取证证明 `E_POINTER` 在客户端里**从来没有被任何代码处理过**
> （全 `.text` 里 `0x80004003` 出现 5332 次、`cmp` 0 次），而 `E_NOINTERFACE`
> 有 1404 次 `cmp` —— 也就是说"接口不可用"早有正规降级通道，是 `E_POINTER`
> 把这条通道截断了。详见第十节。**上游 D3D8 设备未挂载这一根本问题仍然独立存在。**

## 十、修复方案与验证（2026-09-28 已实施）

对象：`tool/client-debug/beidou-unified-patch/patch_unified.py`（唯一入口，从基线全量重建）

### 10.1 三条决定修法形状的证据

| # | 证据 | 含义 |
| --- | --- | --- |
| 1 | `0x40263B` 在 `.text` 内有 **2406** 个调用点，其中 2381 个把返回值直接当 `this` 用 | **绝对不能**把取址器改成"返回 0"，那会把可捕获异常换成 0 地址解引用 |
| 2 | 全 `.text` 中立即数 `0x80004003`(E_POINTER) 共 5332 处：**4927 `push` + 402 `mov` + 3 `add`，`cmp` = 0** | `E_POINTER` 只被"产生"，从不被"分类/处理" → 抛出去一定是致命弹框 |
| 3 | 全 `.text` 中 `0x80004002`(E_NOINTERFACE) 有 **1404 处 `cmp`**；崩溃函数自己在 `0x5CAD25` 就是 `mov ebx,0x80004002` | "接口不可用"是客户端**设计上就有的降级信号**，调用方会接 |

补充物证（崩溃前 100 字节内）：`0x5CAD10 mov [ebp-0x64],ebx` 先把接口槽清 0，
`0x5CAD13 je +0x21` 在源对象为空时**直接跳过 QI**，随后 `0x5CAD25` 装入
`E_NOINTERFACE` —— 即"拿不到接口"这条路本来就打算继续走。
后面 `0x5CADAC` 的取址器却抛 `E_POINTER`，属于**自相矛盾**，不是有意为之。

### 10.2 手段：只在崩溃函数内换调用目标 + 三个"接住空值"的壳

崩溃函数 `0x5CAC3D..0x5CF58C`（19 KB，单出口 `ret 0xc`）内共 **127** 个
`call 0x40263B`。按 CFG 可达性枚举并按消费者分组：

| 组 | 消费者 | 站点数 | 接住 `this == 0` 的桩 |
| --- | --- | --- | --- |
| A | `0x403935`（get_item 包装，`ret 8`，VARIANT 出参） | 119 | **桩D** → 直接出**空 VARIANT**（下游本来就判 `variant.vt`） |
| B | `0x4039F1`（`vtbl[7]`，`ret 4`，DWORD 出参） | 6 | **桩F** → 出参写 0 |
| C | `0x409EEF`（`vtbl[8]`，`ret`，返回 DWORD） | 2 | **桩G** → 返回 0 |

补丁内容（全部原地等长，可从基线一键重建/回滚）：

| 点 | 位置 | 原字节 | 新字节 |
| --- | --- | --- | --- |
| P5a | `0x403965` | `8B 0E 8D 55 E0` | `E9 <rel32>` → 桩D |
| P5b | 127 处 | `E8 <rel32→0x40263B>` | `E8 <rel32→0xAEFEA0>`（只换 4 字节操作数） |
| P5c | `0x4039F5` | `83 65 FC 00 56 8B F1` | `E9 <rel32> 90 90` → 桩F |
| P5d | `0x409EF6` | `8B 06 8D 4D FC 51` | `E9 <rel32> 90` → 桩G |

桩 `0xAEFEA0`（3 字节）就是取址器的容错克隆：

```
0xAEFEA0  8B 01   mov eax,[ecx]     ; 与 0x40263B 的正常路径逐字节等价
0xAEFEA2  C3      ret               ; 差别只有：槽为空返回 0，不抛 _com_error
```

它不碰 `esi`（基线的 `push esi`/`pop esi` 只是为抛异常路径保护寄存器），
不改任何标志位，调用/返回的栈效果与 `call 0x40263B` 完全一致。

### 10.3 为什么这不会"改一处、崩另一处"

* **只动崩溃函数内的 127 个点**。`0x40263B` 本体一字未改 —— 另外 2279 个
  调用点的行为**完全不变**（该抛还抛）。这是与"改共享取址器"的关键区别。
* **桩D/F/G 只在 `this == 0` 时改变行为**，而基线在该条件下分别是
  `mov ecx,[cs:0]`（0x403965）、`mov eax,[cs:0]`（0x4039FC / 0x409EF6）——
  **必然访问违例**。所以三处都是"必崩 → 有定义的默认值"，不引入新崩溃路径。
* **桩D 的栈深度安全**：其空分支跳到 `0x403980`，而那一整段以 `leave`
  收尾（`leave` = `mov esp,ebp; pop ebp` 会重置 esp），入桩时的 esp 偏差
  在函数返回前必然被吸收，`ret 8` 对调用方的净效果不变。
* **`E_POINTER` 无人处理**（证据 2），所以"把异常换成空值"不会让任何
  既有的 `catch`/`cmp` 分支走岔。

P5 的设计是 **「只动崩溃函数内的 127 个点，`0x40263B` 本体一字不改」**（§10.3）——
这是对的（共享取址器有 2406 个消费者，改本体必然波及全局）。
代价就是：**同一个取址器在别处还有 2279 个"该抛还抛"的点**，以及
**内联写死 `E_POINTER` 的站点（如 `0x43FD4E`）根本不走 `0x40263B`，任何"改 call 目标"的方案都覆盖不到。**

也就是说：P5 把「**那一处**切图崩溃点」治好了，但"空槽即抛 `E_POINTER`"这个**机制**还在，
换个入口就复现。这不是"改一处崩另一处"（那里没崩，是被 P5 转成了异常），
而是**同类站点在别处继续冒头**。

  之后才存在 → **跨会话比对象地址不可行**，判定只能在同一份日志内做。

### 12.3 缺口一：引擎每会话只采 8 次栈

`event=first_chance_handler … filters=C0000005/E06D7363/80004003 cpp_stack_samples=8`。
第 9 次起写 `(sample_limit)`。本会话最关键的第 **13/14** 次（弹框前最后两次，相隔 5 ms）
正好在配额之外。**这是取证缺口，不是崩溃原因。**

### 12.4 缺口二：v5 的转储太晚，看不到抛点

转储由 worker 线程写，故障线程已经展开过 throw 帧：

* 异常流 `CONTEXT.Esp = 0x001ADED0`（抛出点）；
* ThreadList 给该线程的 `Stack.StartOfMemoryRange = 0x001AE780`、**`Stack.Rva = 0`**（空描述符）；
* 内存表实际覆盖 `0x001AE6EC..0x001B02F0` —— **全在抛出点之上 2.2 KB**；
* `dump_inspect.py rets` 读到的因此是**展开之后**的链（主线程在 `Gr2D_DX8.dll+0xA113` 渲染路径）。

顺带修好 `dump_inspect.py` 的一处缺陷：空描述符时旧的 `stack_bytes()` 只认"起点完全相等"，
导致**自家转储一律报"栈未落在转储里"**；现在退化为"取包含 `st_start` 的那一段"。
