評判模型：四個維度，機制可還原度是決定性的

維度為什麼重要
① 機制可還原度 決定性因素。客戶端是 GMS 083 系老端，TMS 273 的專屬 UI／新系統（鏡像介面、道場樓層、配對、航海） 在老端根本渲染不出來——這類玩法天然還原不了。反之「打怪／收集／對話／Boss 戰」這類傳統機制， 083 端完全能表達。
② 地圖資源成本 本次 2730 段能閉環，決定性原因就是 24/24 圖已在倉庫。反之 2710 段缺 186 張， 光遷圖就是獨立工程。覆蓋率是最硬的指標。
③ 玩法數據量 任務定義（QuestInfo/Check/Act/Say）、NPC 對話、PQ 腳本要補多少。 照 2730 的經驗，純數據驅動（無過場）一條鏈約 15–30 個任務，可控。
④ 服務端既有支撐 EventInstanceManager 能力完整（計時器／玩家註冊／隊伍／遠征隊／發獎）， 且已有 121 個 event 腳本（LudiPQ、OrbisPQ、CygnusBattle、MonsterPark…）。 經典 PQ 的框架是現成的，不需要造輪子。

六、判断边界（这份结论的适用条件）

  • 「還原度」指玩法可玩性，不含過場演出。按你「保持無過場」的路線， TMS 的 Say 台詞與 startscript/endscript 一律不導入—— 所以最高還原度是「流程完整、劇情演出缺失」。
  • 覆蓋率只看地圖 ID 是否存在，不檢查圖內 life／portal／foothold 是否完整。 實際動手前要像 2730 那樣逐圖核對（本次就發現 24 張圖全缺 lvLimit）。
  • 怪物／NPC／道具不在本表統計內。它們要單獨核對（2730 的經驗： 兩個 boss 是 summonType=1 腳本召喚物，圖上根本沒有）。
  • 客戶端版本是推斷的（GMS 083 系 + 魔改相容 DLL）。 若能確認實際版本支援的 UI 集合，C 級裡「客戶端不支援」的結論可以再精確化。
