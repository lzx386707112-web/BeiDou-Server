能转，但「全改成 4444」有三个真问题，建议不要全量做。
编码不是障碍：老客户端本来就在渲染 323,861 个 ARGB4444 画布，按 AGENTS.md 迁移的技能载荷也是 4444 且能播。真正的障碍是：
① 省的空间集中在「会掉色」的那部分——位逐位无损的画布占 94.3%，但它们的冗余早已被 zlib 吃掉，转过去只小 13.1%；而会掉色的画布能小 53.7%。想省 0.5 GB 就得接受掉色。
② 全量改写要动 48,664 个文件，命中项目里明令禁止的整树重写形态；而且现有增量补丁器对变长替换的拒绝率是 16%（全部落在 Character/ 装备），这条路现在是断的。

1. 体积：省得动，但省的不是你以为的那部分

ARGB4444 的未压缩数据确实是 8888 的一半，但 IMG 里的画布是 zlib 压缩存储，实际能省多少取决于「被丢掉的那 4 位里还剩多少信息量」。

3. 工程障碍（与画质无关，但决定能不能落地）

3.1 变长替换会被工具链拒绝

对 120 个随机文件里第一个 8888 画布，用现成的增量补丁器做「把记录替换成它自己」——变长替换里最温和的情形：接受 68 个、拒绝 13 个（16%）。拒绝信息是 string reference at 0x… points into replaced bytes：有别的记录的字符串引用指向这段字节，缩短它会产生悬空指针，补丁器选择报错而不是写出坏文件。被拒的全部落在 Character/ 装备上。

3.2 唯一结构上安全的路线：等长原地载荷补丁

把载荷区域原地覆盖成同样长度的字节：文件长度不变、不触碰任何 size 字段、不需要重定位任何字符串引用。在 7 个文件上实测：改动字节全部落在载荷区间内、长度不变、重解析无告警。

但这条路有一个仓库内无证据的假设：4444 载荷压缩后通常更短，等长要求把剩余字节补 0。客户端 zlib 解码器是否容忍流结束后的填充字节，本仓库无法验证——必须在实机上先试一个文件，不能假设。

3.3 载荷里藏着一个「一倍零平面」

抽样 191,913 个 8888 画布的载荷里，79.6% 解压出来的字节数是 w×h×4 的整整 2 倍，多出来的后半段 100.0% 全为 0，客户端只读前 w×h×4。
这段冗余原始数据有几百 MB，但全零数据 zlib 压完几乎没有成本——去掉它只回收 2.9%。所以它不是一个可回收空间，而是一个必须理解的坑：任何把载荷当成 2 倍像素来处理的工具都会画错；decode_canvas 现在“能用”只是因为 PIL 恰好忽略了多余字节。

4. 建议

不要全量。按「收益 ÷ 风险」排序，只做窄子集。
  • 第一优先：只转「位逐位无损」的画布（94.3% 个、70% 体积）。像素零变化、可自动判定、无需人眼验收，约省 198.0 MB。这是唯一能全程自动化的部分。
  • 第二优先（需人眼验收）：Character/Weapon + Character/Cap，合计可省 414.8 MB，但这两块同时是掉色最重的（约 43% / 59% 体积），必须先截图比对装备外观再决定。
  • 不要碰：Item/Install、Map/Tile、Morph（已 100% 是 4444）、Skill（99% 无损且省得极少）、Effect / UI（89% / 93% 会掉色，收益还小）。
  • 绝对不能碰 Skill/ 里已按 AGENTS.md 转成 4444 的迁移技能载荷。那是规范红线，format=1, format2=0 必须保住。
  • 验证门槛（缺一不可）：① 生成器跑两遍、哈希一致；② 载荷区间外字节逐字节不变；③ 解析无 truncated、无 parse_warnings；④ 抽样画布解码出可见像素且尺寸不变；⑤ 真机启动 + 进游戏看装备 / 头发 / 特效 / UI。前四条仓库里能做，第五条只有你能做。
