## 一、结论（一句话版）

手机客户端在「进入游戏 · 加载期」抛出**未处理的 `_com_error`，HRESULT = `0x80004003` `E_POINTER`（无效指针 / `-2147467261`）**，
被客户端**自带的顶层异常过滤器**接住 → 弹框 → `ExitProcess code=0` → 窗口消失。玩家看到的就是"选完人一进去就闪退"。

**不是访问违例**（无 `code=0xC0000005`、无 `first_chance_av`、无 `event=crash`），
**不是某个 hook 把内存写坏了**（各兼容 DLL 日志全绿，7 个模块 CheckSum 与仓库逐一相符）。

**与 PC 的差别不在"机制"，而在"时机 + 一条手机独有的内存映射失败"**：

- 机制相同：两端都是同一个 `0x40263B` 取址器发现某个 COM 智能指针为空 → 抛 `E_POINTER`；
- 时机不同：PC 撑进了游戏（45 秒可交互窗口），手机**在加载期就死**（进游戏后约 0.4 秒）；
- **手机独有**：`MapViewOfFile` 连续 3 次返回 NULL 且 `GetLastError()=8`（`ERROR_NOT_ENOUGH_MEMORY`），PC 一次都没有。

## 三、异常本体与抛点

### 3.1 异常类已被二进制确认

手机 `first-chance` 转储的 `pThrowInfo = 0x00B44B18`，其 `pCatchableTypeArray → _CatchableType → _TypeDescriptor`
的地址是 **`0x00BD8270`**，内容是：

```
0x00BD8270  vftable=0x00B41248  spare=0  ".?AV_com_error@@"
0x00BD8290  vftable=0x00B41248  spare=0  ".?AVZException@@"
0x00BD82B0  ...  ".?AVCMSException@@"
0x00BD82D0  ...  ".?AVCTerminateException@@"
```

⇒ 抛的就是 MSVC／ATL 的 **`_com_error`**；客户端自有的异常体系是 `Z*`（`ZException`），
且客户端代码里**确实有 `catch(_com_error&)` 与 `catch(ZException&)` 两类处理器**（见 §五末）。

**抛框文案的解码**（与用户截图逐字吻合）：

```
error code : -2147467261 (Unknown error 0x80004003)
             └ 0x80004003 的十进制 = E_POINTER = "无效指针"；"Unknown error 0x%0lX" 在 0xB3D8E8
```

⇒ **`error code : -2147467261` 与 `(Unknown error 0x80004003)` 是同一个 HRESULT 的两种写法**。
这条同时排除了「参数错误 / `E_INVALIDARG 0x80070057`」（全 exe 只有 3 处 `push 0x80070057`）、
`STG_E_FILENOTFOUND`、以及任何 AV 方向。

### 3.2 抛点与调用链

`0x40263B` = 智能指针取址器（本项目文档里叫"空则抛访问器"），**2406 个调用点、本体不许改**：

```asm
0040263b  56             push   %esi
0040263c  8b f1          mov    %ecx,%esi
0040263e  83 3e 00       cmpl   $0x0,(%esi)      ; *ecx == 0 ?
00402641  75 0a          jne    0x40264d
00402643  68 03 40 00 80 push   $0x80004003      ; E_POINTER
00402648  e8 97 d7 65 00 call   0xa5fde4         ; _com_raise_error  ★
0040264d  8b 06          mov    (%esi),%eax
0040264f  5e             pop    %esi
00402650  c3             ret
```

即：**ecx 指向一个"应该非空"的智能指针槽，它是 NULL。**

`dump_inspect.py rets` 对手机 `first-chance-cpp-…pid32…dmp`（tid=0x24）的逐帧校验
（每帧都通过「栈值落在模块内 + 前置指令是 `E8 rel32`」双重校验）：

```
栈 0x0012EBC4  ret 0x00A605E7 [BeiDou.exe+0x6605E7]  ← E8 @0x00A605E2 → +0x660BB7
栈 0x0012EBE4  ret 0x009F6108 [BeiDou.exe+0x5F6108]  ← E8 @0x009F6103 → +0x6605C3  ★ 抛点
栈 0x0012F204  ret 0x0042FE9E [BeiDou.exe+0x2FE9E]
栈 0x0012F21C  ret 0x0042D9B1 [BeiDou.exe+0x2D9B1]
```

> ⚠️ **这条推翻了 `docs/崩溃诊断-启动期COM异常弹框-20260929.md` §二.2 里「`0x5F6108` 落在指令中段、是栈上数据」的旧判定。**
> 上一轮之所以判错，是因为用「固定 thunk 地址（`0xA5FDE4`）反查」——而 `0x65FDEA` 处的 `e8` 其实是
> `ret $0x4` 尾部字节 `c2 04 00`。**正确做法是扫 `call 0x40263B` 站点 + 栈值/前置 call 双校验。**

```asm
9f60b6  cmpl $0x0,0x38(%eax)        ; 对象 +0x38 为空？

9f60cb  mov  0x38(%eax),%eax
9f60ce  mov  %eax,-0xac(%ebp)       ; 保存指针
9f60d4  mov  -0xd30(%ebp),%eax
9f60da  andl $0x0,0x38(%eax)
9f60de  mov  -0xd30(%ebp),%eax
9f60e4  andl $0x0,0x34(%eax)
9f60e8  movl $0x1,-0xd04(%ebp)
9f60f2  cmpl $0x0,-0xd04(%ebp)
9f60f9  je   0x9f6108
9f60fb  push $0x0
9f60fd  push -0xac(%ebp)
9f6103  call 0xa605c3               ★ HRESULT = 该指针的**低 16 位**（错位抛出）
9f6108  mov  -0xd30(%ebp),%eax
9f610e  cmpl $0x0,0x34(%eax)        ; +0x34 再来一遍
```

**要点：**

1. 这是 `smartptr` 的**拷贝/移动语义**（`+0x34` / `+0x38` 两个成员各一次），
   而不是"取址器空则抛"。所以 **`0x9F6103` 不是 `call 0x40263B` 站点**，P5 的站点表**永远盖不到它**——
   任何"改 call 目标"的补丁形状对它无效，只能改成"内联展开 + 前置判空"。
2. 这一处的 HRESULT 是**从被搬运的指针值低 16 位取出来的**，所以它不是"有意抛 E_POINTER"，
   而是**对象处于半构造/半析构状态**时误把它当 HRESULT。这更像"生命周期 bug"，不像"资源缺失"。
3. 手机转储只在**第 1 次**异常时落盘（`beidou_diagnostics.ini: dump_first_chance_cpp_after=1`），
   所以 occ5 的完整现场**没有转储**，目前只有 `VellumVideoCompat.log` 的栈摘要。

## 五、抛点全谱：一族"vtbl 包装" + 一张站点表

`tool/client-debug/beidou-unified-patch/README.md` 已经把这几个函数定性了，本轮把它们和抛点对上：

| 包装函数 | 语义 | 出参 | 基线里 `this==0` 会怎样 | 该函数内的抛点 |
|---|---|---|---|---|
| `0x403935` | `this->vtbl[5](…)` | VARIANT（`ret 8`） | `mov eax,[cs:0]` → **必崩** | 手机 occ1/occ3 的**上游**；PC 侧同类 |
| `0x4039F1` | `this->vtbl[7](…)` | DWORD（`ret 4`） | 同上 | — |
| `0x409EEF` | `this->vtbl[8](…)` | DWORD（`ret`） | 同上 | **PC occ1/2/3 站点 `0x40A492` 在它体内** |
| `0x4052AD` | `QueryInterface(riid=0xBD8308)` 包装 | 接口指针 | **空则返回 `E_NOINTERFACE 0x80004002`，不抛** | — |
| `0x4032B2` | `VARIANT → IUnknown*` | 接口指针 | **非 dispatch/unknown 变体返回 NULL，不抛** | — |
| `0x40291D` | `VariantClear` 包装 | HRESULT | **FAILED 才抛** | — |

读法：**下游客错，上游必抛。** `0x4052AD`/`0x4032B2` 这两个"接住空值"的设计说明
源码里本来就打算"接口拿不到就降级"（`E_NOINTERFACE` 在 `.text` 里有 1404 次 `cmp`，是正规降级信号），
**矛盾点全在最前面那一次"认为绝不可能为空"的解引用上**。

本轮新解出的常量：

```
0xBD8308 = {986515D9-0A0B-4929-8B4F-718682177B92}   ← 客户端自有接口的 IID（0x4052AD 在 QI 它）
0xBD8318 = {57DFE40B-3E20-4DBC-97E8-805A50F381BF}
0xBD8338 = {00020404-0000-0000-C000-000000000046}   ← IEnumVARIANT
0xBCC508 = HandlerType 表：{adjectives=8, pType=0xBD8270(com_error), disp=-0x1C, handler=0x9F2262}
                            {adjectives=8, pType=0xBD8290(ZException), disp=-0x38, handler=0x9F22F0}
```

⇒ 客户端在这片代码里**同时 `catch(_com_error&)` 和 `catch(ZException&)`**——
说明这条链上的异常**本意是被接住的**。手机这次没被接住（走了顶层过滤器），
要么是抛点落在 `try` 区间之外，要么是**栈被破坏/展开失败**。

### 手机 3 个站点（都不在 P5 的 `0x5CAC3D..0x5CF58C` 内）

形状完全一样：**先取对象 → 空则抛 → 再 `vtbl[5]` 包装取 VARIANT → 转接口 → QI**。

```asm
; 站点 0x5296C9（occ1/3）
5296c2  lea  -0x20(%ebp),%ecx
5296c5  movb $0xd,-0x4(%ebp)          ; SEH tryLevel
5296c9  call 0x40263b                 ★ E_POINTER
...
5296e6  call 0x4032b2                 ; VARIANT → 接口
5296fc  call 0x4052ad                 ; QI(IID 0xBD8308)
529703  jge  0x52970f
52970a  call 0xa5fde4                 ; QI 失败 → 也抛（但这里失败会先被 E_NOINTERFACE 分支吃掉）

; 站点 0x527963（occ2）
527950  call 0x79e805                 ; push $0x6c0 之后：取"槽"
527955  mov  %eax,%ecx ; 527957 call 0x406292
52795c  lea  -0x1c(%ebp),%ecx
527963  call 0x40263b                 ★ E_POINTER
527972  call 0x403935                 ; vtbl[5] → VARIANT
52797c  call 0x414d40                 ; 真正的业务调用

; 站点 0x639B81（occ4）
639b72  lea  0x30(%esi),%ebx          ; 对象内偏移 +0x30 的成员
639b7c  mov  %ebx,%ecx
639b81  call 0x40263b                 ★ E_POINTER
```

`0x79e805` 的常量 `0x3c1` / `0x6c0` 与 `0x59A2E9/0x59A306`（同一 `ecx = 全局对象 0xBEC33C` 反复调用、
一个返回值丢弃一个写 `[ebp-0x28]`）表现为 **"从某个容器里弹出/遍历条目"**；
`0x9F4E54` 序言处内联写字符串 `\kernel32.`，并在附近调用 `GetSystemDirectoryA`。
**这两个函数的业务名字本轮仍未确定**（全 exe 只剩 16 个 RTTI 名，符号基本被剥），
但**不影响定性与下一步**：它们是"取一个本该存在的接口/资源"，取到 NULL。

> 结论：**这三个站点与 PC 的 `0x40A492` 是同一个源码宏/内联展开的不同实例**，
> 所以"手机和 PC 抛点不同"**不是**"两条不同的代码路径"，而是**同一段逻辑在处理不同对象**。

### 6.1 ★ 手机独有：`MapViewOfFile` → `ERROR_NOT_ENOUGH_MEMORY`

```
12:01:03.701 [seq=35] [tid=36] MapViewOfFile mapping=00000158 result=00000000 err=8 access=0x00000004 offset=0:0 bytes=0
12:01:03.789 [seq=36] [tid=36] MapViewOfFile mapping=000001B4 result=00000000 err=8 access=0x00000004 offset=0:0 bytes=0
12:01:03.793 [seq=37] [tid=36] MapViewOfFile mapping=000001B8 result=00000000 err=8 access=0x00000004 offset=0:0 bytes=0
```

* 三条紧跟 `12:01:03.684 event=resource_open api=fopen status=ok … path="E:\amxd\mxd\List.wz"` 之后；
* `result=00000000` = 视图地址 **NULL**（映射失败是硬事实）；`err=8` = **`ERROR_NOT_ENOUGH_MEMORY`**；
* `access=0x00000004` = `FILE_MAP_READ`，`bytes=0` = 整文件；
* 退出期 `incident_mapping` 里同样有 3 条 `MapViewOfFile … result=00000000 error=8`（seq 119/143/145），
  同一时刻其它映射是成功的（`result=02010000` 等）→ **不是全局耗尽，是"特定尺寸/对齐的视图映射失败"**。

> **【第三轮修正】** 本节最初推断"被映射的是 List.wz（13 KB），所以不是真缺内存"——**错**。
> 12:01 会话 `log_successful_mappings=0`，失败行不带文件名，`fopen List.wz` 只是时间上邻近。
> 13:21 会话打开成功映射日志后钉死：**失败的是 `Mob.wz` / `Sound.wz` / `Map.wz` 三个最大档案**，
> `Character.wz` 落点 `0x7FFF0000` 证明 2 GB 用户地址空间封顶——大档案找不到连续空洞，`mmap` 返回 `ENOMEM`。
> "Wine/Box86 地址空间"的方向是对的，但机制是**2 GB 上限 + 大档案 + 碎片化**，不是 13 KB 小文件分配失败。
> 详见文首「第三轮」§1。

> 这条为什么重要：**PC 的 `MapViewOfFile` 全成功、手机失败 3 次**，恰好能解释
> "电脑能正常玩、手机一进游戏就崩"——因为这条链上游正是"映射/装载资源 → 失败返回 NULL →
> 智能指针为空 → `0x40263B` 抛 `E_POINTER`"。

**但必须诚实标注不确定度**：这条因果链的第 3 跳（NULL → 具体哪个智能指针）**尚未直接观测到**，
因为手机转储里 `0x9F4E54` 的现场只有 occ5 那一次没有转储，occ1 的 `0x12EBE8..0x12F210` 中间帧也没进转储。

## 附：本轮新增的可复用手法（写给下次）

1. **判异常类**：`dump_inspect.py exc` 给的 `pThrowInfo` → `_s__ThrowInfo.pCatchableTypeArray`
   → `_CatchableType.pType` → `_TypeDescriptor`（`.?AV…@@` 字符串）。
   手机上 `pObject` 的 `+0/+4` **不能当 `m_hr` 读**（本机实测 `+0=1, +4=2`），
   **HRESULT 必须以弹框文案 / observer 日志为准**。
2. **找 FuncInfo 归属**：`mov $imm32,%eax ; call 0xA60B98(__EH_prolog)` 里的 `imm32` 就是 `_s__FuncInfo`
   （首 dword `0x19930520`）；`FuncInfo.pTryBlockMap → TryBlockMapEntry.pHandlerArray → HandlerType`
   能直接给出**该函数里 `catch` 了哪些类型**、handler 地址在哪。
3. **反查抛点**：不要用「固定 thunk 地址向前搜 `E8`」（会撞上 `ret $0x4` 的 `c2 04 00` 尾部字节而误判）。
   正确做法：扫 `call 0x40263B` 的站点表 + 栈值落在模块内 + 前置指令是 `E8 rel32` 三重校验。
4. **Windows 错误码**：`err=3` = `ERROR_PATH_NOT_FOUND`；**`err=8` = `ERROR_NOT_ENOUGH_MEMORY`**；
   `err=2` = `FILE_NOT_FOUND`；`err=6` = `INVALID_HANDLE`。日志里裸的 `err=N` 是 Win32 错误码，不要猜。
